# 自主获取信息：能自己查到的，不要问用户

核心原则：**Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料，只是多一轮往返。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

## 1. 四种自主获取手段

| 手段 | 能拿到什么 | 怎么做 |
| --- | --- | --- |
| 项目勘察 | 工具清单、已有计数器/TODO/状态栏实现、消息拼装位置、约束阈值、模型与服务商、语言风格 | `scripts/discover_context.py` + 定向检索（见第 2 节） |
| 文档与网页检索 | 服务商缓存计费与 α、缓存命中规则、模型是否支持 `tool_search`、平台差异 | 用 `web_search` / `web_fetch` 查官方文档与仓库，**不要凭记忆给数值** |
| 本地实测 | S / R / N、缓存命中率、思考 token 量、延迟与成本 | 跑样本轨迹 + `cache_cost_estimator.py` + 埋点统计 |
| 对照实验 | 某项技术是否真的有效 | 有/无该技术的 A/B，见 `techniques.md` 的消融指标 |

判定顺序：**先项目 → 再文档/网页 → 再实测 → 仍不确定且属业务决策，才问用户。**

## 2. 项目勘察清单

| 目标 | 检索方式 |
| --- | --- |
| 工具清单与数量 | `grep -rn "\"name\"" --include=*.py`、`grep -rn "tools\s*="` |
| 已有状态栏 | `grep -rn "agent_status\|system-reminder\|status_bar"` |
| 已有计数器 | `grep -rn "call_count\|counter\|invoked\|调用次数"` |
| 已有 TODO | `grep -rn "todo\|rewrite_todo\|update_todo"` |
| 消息拼装位置 | `grep -rn "messages.append\|role.*system\|messages.create"` |
| 约束与阈值 | `grep -rn "max_calls\|max_retries\|limit\|budget\|timeout"` |
| 模型与服务商 | `grep -rn "model\s*=\|claude-\|gpt-" ` |
| 缓存配置 | `grep -rn "cache_control\|ephemeral\|defer_loading\|tool_search"` |
| 轨迹样本 | `grep -rln "tool_calls"` 的日志目录 |

自动化：`python scripts/discover_context.py <项目目录> --trace trace.jsonl`，输出事实（带 `文件:行` 证据）与推断的默认方案。

脚本**只遍历源码与文档**，默认跳过与状态栏设计无关的文件：构建产物与依赖（`dist/ build/ out/ target/ node_modules/ __pycache__/ .venv/ vendor/` 等）、编译产物与二进制（`*.pyc *.so *.class *.jar *.wasm` 等）、压缩打包（`*.min.js *.bundle.js *.map`）、锁文件（`package-lock.json` `yarn.lock` `poetry.lock` 等）、生成代码（文件头含 `Code generated by` / `DO NOT EDIT` / `@generated`）。可用 `--max-file-size`（KB，默认 300）、`--max-line`（默认 1000，跳过压缩后的长行）调整。

## 3. 从样本估算 S / R / N

| 参数 | 估算方法 |
| --- | --- |
| N（更新次数） | 多条轨迹轮数的中位数，至少取 5-10 条 |
| R（轮间新增后缀） | 相邻两次状态更新之间的消息 token 之和 |
| S（单条状态） | 按确定的字段集实际渲染一次后计 token |
| α（缓存单价倍数） | 服务商定价文档；查不到先按 0.1 试算并**标注为假设** |

粗略换算：中文 1 字 ≈ 1 token，英文 4 字符 ≈ 1 token。估算只用于选策略，最终以实测命中率校准。

## 4. 能从项目里直接推断的结论

| 勘察发现 | 推断 |
| --- | --- |
| 工具参数中重复出现同一字段（如 `target`、`path`） | 计数默认按该字段分组，而非只做全局计数 |
| 已存在状态栏注入代码 | 沿用现有注入点，只改渲染内容 |
| 配置中已有 `max_calls` 类阈值 | 直接复用，不重新定义业务规则 |
| 项目注释与文档为中文 | 状态栏语言默认中文 |
| 会话日志已落盘 | 复用做对照实验与审计 |
| 轨迹平均轮数 > 3 | 默认启用 TODO |

## 5. 什么才必须问用户（业务决策）

只有这几类：**查不到、且属于人的取舍**：

1. **业务规则与阈值**：调用上限是多少、超限后是拒绝还是降级——产品决策。
2. **产品取舍**：体验优先还是成本优先（直接影响更新策略与压缩力度）。
3. **权限与合规边界**：哪些数据不能进上下文、是否需要审计留痕。
4. **目标权重**：多个指标冲突时以哪个为准。

提问要求：
- 一次 **≤3 个问题**，每个给 **2-4 个选项**。
- **必须标明推荐项与推荐理由**（依据写清来自哪个文件/哪次实测）。
- 绝不问能从项目或文档里读到的信息（工具数量、模型名、现有限制等）。
- 用户说「你定」或不回复 → 采用推荐项，在 `assets/requirements_intake.md` 记为**假设**并注明复核时间。

## 6. 常见坑

- **凭记忆给数值**：α、模型能力、缓存规则请以文档为准。
- **只看提示词不看代码**：约束的真实实现通常在代码里，两边不一致时以代码为准。
- **把配置默认值当业务决策**：默认值 ≠ 业务规则，涉及规则才找产品确认（这是**确认**，不是**询问**）。
- **样本偏差**：只用一条轨迹估算 N 会失真。
- **忽略已有实现**：项目里可能已有部分计数或 TODO，复用优于新建。
