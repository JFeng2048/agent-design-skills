# RAG 管线设计（编码实现指导）

RAG（Retrieval-Augmented Generation，检索增强生成）的核心思想是**把 LLM 的思考与生成能力，和外部知识库的广度与时效性结合**：模型训练数据有截止日期，知识库可以随时更新。

典型 RAG 系统由两部分构成：**检索器**从知识库找出相关片段，**生成器**（通常是 LLM）拿这些片段作为上下文生成答案。核心流程是：

```text
① 检索 Retrieval → ② 增强 Augment → ③ 生成 Generate
查询 → Top-K 文本块      查询+检索结果构造 Prompt     LLM 基于上下文生成
```

**本 skill 的定位是编码实现指导，不是提示词模板**：产出是分块策略、索引与检索管线、融合与重排序、度量与调优方案，载体是代码，不是一段提示词。

## 动手前：自己把需求调研清楚，尽量不问用户

**核心原则：Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

### 1. 自主调研（项目 → 文档 → 线上数据）

| 手段 | 能拿到什么 | 做法 |
| --- | --- | --- |
| 项目勘察 | 现有向量库与索引类型、嵌入模型、分块配置、是否有 BM25/重排序、查询日志 | `python scripts/discover_rag_context.py <项目目录>` + 定向检索（见 `references/information-gathering.md`） |
| 文档与检索 | 嵌入模型维度与长文本上限、ANN 索引特性、重排序模型、基准结论 | 用 `web_search` / `web_fetch` 查权威来源，**不要凭记忆给结论** |
| 线上数据 | 真实查询分布、低召回/低精度的查询类型、点击与反馈 | 读查询日志；按查询类型分类归因 |
| 实测 | recall@k / MRR / nDCG、分块质量、延迟与成本 | 跑标注集 + `scripts/retrieval_eval.py` + 对照实验 |

判定顺序：**先项目 → 再文档/检索 → 再线上数据与实测 → 仍不确定且属业务决策，才问用户。**

### 2. 推断默认方案（可直接落地）

- **分块**：默认**递归/结构感知切分**（生产系统最常用的默认选择）；起点 256-1024 token、重叠 10%-20%，再按检索质量调优。
- **检索**：默认**混合检索**（稠密 + 稀疏），因为没有任何单一策略在所有场景可靠。
- **稠密**：语义相近优先，选上下文感知的句向量模型（如 BGE-M3 类），注意其输入长度上限。
- **稀疏**：BM25 默认 `k1=1.5`、`b=0.75`，倒排索引支撑精确关键词匹配。
- **融合**：RRF，`score = Σ 1/(k + rank)`，`k=60`。
- **重排序**：对融合后 Top-N（如前 50）用跨编码器精排。
- **指标**：以 **recall@k** 为主（最贴近 RAG 需求），辅以 MRR、nDCG 与检索失败率。

### 3. 只有业务决策才问用户

必须问的只有这几类（查不到、且属于人的取舍）：

1. **知识范围与更新频率**：哪些文档入库、多久更新一次（直接影响索引选型）。
2. **成本与延迟的权重**：是否上重排序（更准但更慢）、ANN 索引的内存预算。
3. **精度与召回的取舍**：宁可多召回让 LLM 筛选，还是严格控制噪声。
4. **数据边界**：哪些文档可入库、是否有权限分级（检索需不需要按权限过滤）。

提问要求：一次 **≤3 个问题**，每个给 2-4 个选项，**标明推荐项与推荐理由**；用户说「你定」→ 采用推荐项并记为假设，写入 `assets/requirements_intake.md`。

## 设计流程（按序执行）

### 1. 先定度量：没有指标就无法调优
产出：标注查询集 + 指标口径（recall@k / MRR / nDCG / 检索失败率）。
- **recall@k**：包含正确答案的文档出现在前 k 个结果中的查询比例——回答「该找的找到了吗」，**最贴近 RAG 需求**。
- **MRR**：第一个相关文档排名的倒数取平均——回答「找到得够不够靠前」。
- **nDCG**：综合所有相关文档的排名与相关程度，越靠后折扣越大——回答「整个排序列表质量如何」。
- **检索失败率**：正确信息未出现在 top-20 的查询比例（工业界常用）。
- 用 `scripts/retrieval_eval.py` 计算。详见 `references/hybrid-retrieval.md`。

### 2. 文档分块（离线预处理）
产出：分块策略 + 块大小与重叠参数。
- 为什么必须分块：① 嵌入模型有输入长度限制，且整篇压缩成一个向量会让多主题混杂，向量无法精确表达任何一个（与 Enhanced Notes 同源问题）；② 检索目标是把相关内容注入上下文，片段太大会带入无关内容、稀释注意力。
- 三类策略：
  - **固定大小切分**：按固定 token 数（如 512），相邻块保留 50-100 token 重叠。简单可预测，但会拦腰截断段落、代码、表格。
  - **递归/结构感知切分**：按章节标题、段落、句子等自然边界递归切分，超长时降级到更小边界。**Markdown/HTML 等有显式结构的文档尤其适合，是生产系统最常用的默认选择**。
  - **语义切分**：在相邻句子嵌入相似度的「断崖」处下刀，块内主题单一，代价是额外嵌入计算。
- 权衡：块太小 → 语义模糊（「该公司收入增长了 3%」——哪家公司？）；块太大 → 向量被稀释、带入噪声。起点 256-1024 token、重叠 10%-20%。
- **固有缺陷**：分块会切断片段与原始上下文的联系（指代词、出处）。后文「上下文感知检索」正面解决。
- 用 `scripts/chunk_inspector.py` 体检分块结果。详见 `references/chunking.md`。

### 3. 稠密检索：嵌入模型 + ANN 索引
产出：模型选型 + 索引类型 + 相似度度量。
- 嵌入把文本映射为向量，**语义相近则向量距离近**；用**余弦相似度**（夹角）而非欧氏距离——关心方向（语义）而非长度（文本长度/词频）。
- 模型演进：Word2Vec（静态词向量、共现关系）→ GloVe → BERT（上下文感知、自注意力）→ Sentence-BERT（句级、孪生网络对比学习）→ BGE-M3（多语言、长文本、混合训练）。**静态词向量无法处理一词多义**（bank 的河岸与投行）。
- 大规模检索需要 **ANN（近似最近邻）**索引：
  | 特性 | ANNOY（基于树） | HNSW（基于图） |
  | --- | --- | --- |
  | 构建速度 | 快 | 较慢 |
  | 内存占用 | 低 | 较高 |
  | 增量更新 | 不支持（需完全重建） | 支持（长期增量后建议定期重建以保持精度） |
  | 查询精度 | 较高 | 极高 |
  | 适用场景 | 数据不常变的静态数据集 | 需要实时索引新信息的动态场景 |

  选择索引与选择嵌入模型同等重要，直接决定性能、成本与可维护性。
- 详见 `references/dense-embedding.md`。

### 4. 稀疏检索：BM25
产出：分词与停用词策略 + BM25 参数。
- 根基是**词袋模型**（只关心词是否出现与次数，忽略词序）→ TF-IDF → **BM25**。
- BM25 的两个关键修正：**词频饱和**（k1 控制，出现 10 次不会是 5 次的两倍贡献）与**长度归一化**（b 控制，避免长文档偏倚）。默认 `k1=1.5`、`b=0.75`。
- IDF 形式：`ln((N - df + 0.5)/(df + 0.5))`；当词出现在超过半数文档时取值会变负，**实现中需设下限**。
- **倒排索引**：从词到文档的反向映射（如同书后术语索引页），是稀疏检索快的原因。
- 优势：技术代码、人名等精确查询极佳；局限：读不懂同义表达。
- 用 `scripts/bm25_calc.py` 验证参数与手算结果。详见 `references/sparse-embedding.md`。

### 5. 混合检索与重排序
产出：融合方式 + 重排序范围与模型。
- **为什么混合**：稠密懂语义但可能漏关键词（搜 `HTTP-403` 返回「服务器错误」的泛泛讨论）；稀疏精确但读不懂同义词（搜 `kitty` 找不到只写 `cat` 的文档）。
- 三阶段流水线：
  1. **并行检索**：稠密与稀疏各自召回候选。
  2. **结果融合**：两路得分尺度不同（余弦 0-1 vs BM25 任意正值），**RRF** 抛开原始得分只看排名：`score = Σ 1/(k + rank)`，k 常取 60。简单稳健，但丢失原始得分的相关性信号。
  3. **神经重排序**：对融合后 Top-N（如前 50）用**跨编码器**精排。**重排序不是为补救 RRF**，而是换用更强的匹配范式——双编码器（Bi-Encoder）各自独立编码、快但浅；跨编码器（Cross-Encoder）把查询与文档拼接后逐词比对，慢但准。
- 融合负责产生统一候选池，重排序负责在候选池上精排——**两者不互相替代**。
- 候选池到最终 Top-K 之间还有**多文档配额分配**（见第 6 步）。
- 详见 `references/hybrid-retrieval.md`。

### 6. 多文档配额分配（候选池 → 最终 Top-K）
产出：K 个名额在文档间的分配规则 + α 参数。
- 重排后得到候选片段，可能来自多个文档。**直接按分数取 Top-K 有三个问题**：单文档霸屏、硬性「单文档最多 N 条」在只有该文档相关时导致信息不足、候选不足时名额浪费。
- 解法是按文档相关性**比例分配配额**（最大余额法）：
  1. `rel(d) = max(该文档所有候选片段的分数)`
  2. `w_d = rel(d)^α / Σ rel(d)^α`
  3. `q_d = floor(K · w_d)`，余位按小数部分降序 +1，钳制 `q_d ≥ 1`
  4. 每个文档内按分数取前 `q_d` 条
  5. 候选不足配额时，缺口按顺位回填给其他文档
- 参数：`K`（5-20，由上下文窗口定）、`α`（默认 1.0，**需实验确定**）、`QUOTA_MIN=1`、`QUOTA_MAX`（默认不限）。
  α=1 严格按比例；α<1 向平均倾斜保护低分文档；α→0 完全平均；α>1 向高分倾斜。
- 特性：纯函数、O(N log N)、**零 LLM 调用**、可单测、延迟可忽略；与决定总 K 值的逻辑是上下游关系。
- 不解决**文档内片段冗余**——那是 MMR / xQuAD 的职责，可叠加（配额管「文档间怎么分」，xQuAD 管「文档内选哪几条」）。
- 用 `scripts/quota_allocator.py` 验证并用 `--alpha-sweep` 定 α。详见 `references/multi-document-quota.md`。

### 7. 增强与生成
产出：上下文注入方式。
- 把检索结果作为上下文注入 Prompt，让 LLM 基于上下文回答；要求**引用来源**、无依据时说明不知道。
- 注入顺序与上下文预算联动（见 `system-prompt-design` 与 `agent-status-design` 的上下文管理原则）。
- 注意：检索到的内容属于**外部内容**，需用来源标记包裹，防止提示注入。

### 8. 验收与调优
产出：指标对照表 + 调优结论。
- 按查询类型拆解指标（语义相似 / 精确名称 / 多语言 / 技术代码），定位哪类查询是短板。
- 逐项消融：分块策略、嵌入模型、索引、融合、重排序各自的贡献。
- 观察重排序带来的**排名变化**，验证是否把被单一方法低估的相关文档提到顶端。

## 交付前自检清单

**调研与定位**

- [ ] 已自主调研项目并留下 `文件:行` 证据，未把可查到的信息抛给用户
- [ ] 嵌入模型、索引、重排序模型的结论来自文档检索，非凭记忆
- [ ] 默认方案已给出且可直接落地
- [ ] 需要用户拍板的只剩业务决策，≤3 项且每项带选项与推荐项

**分块**

- [ ] 按文档类型选了策略（结构化文档用递归/结构感知切分）
- [ ] 块大小在 256-1024 token、重叠 10%-20% 区间内并有实测依据
- [ ] 用 `chunk_inspector.py` 检查过：无大量过小/超大块，结构边界未被拦腰截断
- [ ] 已识别分块切断上下文的问题，并有补偿措施（块内保留标题路径/出处）

**检索**

- [ ] 稠密与稀疏并行（混合检索），而非单一路
- [ ] ANN 索引类型与数据更新频率匹配（静态 → ANNOY；动态 → HNSW）
- [ ] BM25 参数明确（k1、b），IDF 有下限处理
- [ ] 融合用 RRF（k=60）或其他可解释方式
- [ ] 重排序范围明确（Top-N），且知道它不替代融合

**配额分配**

- [ ] 候选池到 Top-K 之间有多文档配额分配，不是直接按分数截断
- [ ] 未用「单文档最多 N 条」的硬限制代替动态配额（单文档场景应自动拿满 K）
- [ ] 配额总名额严格等于 K，缺口有回填
- [ ] α 已用 `--alpha-sweep` 实验确定，而非默认了事
- [ ] 分数可能为负时已做平移处理（否则 rel^α 在小数 α 下无定义）
- [ ] 已观测文档覆盖率与单文档最大占比

**评估**

- [ ] 有带标注的查询集，指标以 recall@k 为主
- [ ] 指标按查询类型拆解（语义/精确/多语言/代码）
- [ ] 检索失败率（top-20 未命中）已统计
- [ ] 每项改动都有消融对照记录

## 常见反模式

| 反模式 | 后果 | 修正 |
| --- | --- | --- |
| 整篇文档不切块直接嵌入 | 多主题混杂，向量无法表达任何一个 | 分块后再嵌入 |
| 固定大小硬切结构化文档 | 段落、代码、表格被拦腰截断 | 改用递归/结构感知切分 |
| 只用稠密检索 | 技术代码、人名等精确查询漏召回 | 加 BM25 混合 |
| 只用 BM25 | 同义表达查不到 | 加稠密检索 |
| 直接把两路得分相加/加权 | 尺度不同（0-1 vs 0-几十），排序失真 | 用 RRF 等按排名融合 |
| 用重排序替代融合 | 候选池本身有偏，精排救不回来 | 先融合产生候选池，再精排 |
| 对全量结果做重排序 | 延迟与成本失控 | 只对 Top-N（如前 50）精排 |
| IDF 未设下限 | 词出现在过半文档时 IDF 为负，得分异常 | 实现中设下限 |
| 只看「感觉准不准」 | 无法归因与调优 | 建标注集，量化 recall@k / MRR / nDCG |
| 不查项目直接问用户一堆开放问题 | 用户还得自己去查 | 项目/文档/线上数据能拿到的自己拿 |
| 重排后直接按分数截断取 Top-K | 单文档霸屏，其他相关文档进不来 | 用多文档配额分配 |
| 用「单文档最多 N 条」硬限制防霸屏 | 只有该文档相关时信息不足 | 配额动态计算，单文档场景自动拿满 K |
| 配额分配后不管文档内冗余 | 同一文档多条高度相似，浪费名额 | 叠加 MMR / xQuAD 处理文档内去冗余 |
