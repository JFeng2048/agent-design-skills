# 混合检索：两全其美的艺术

两种方法各有盲区：

| 方法 | 盲区 | 例子 |
| --- | --- | --- |
| 稠密检索 | 懂语义但可能漏掉关键词 | 搜 `HTTP-403`，可能返回「服务器错误」的泛泛讨论 |
| 稀疏检索 | 精确匹配但读不懂同义词 | 搜 `kitty`，找不到只写了 `cat` 的文档 |

**混合检索的思路**：两个引擎都跑，结果合并。**难点在于如何把分布迥异的两组得分整合成一个有意义的排序。**

## 1. 三阶段流水线

```text
用户查询
  → ① 并行检索：稠密（语义）+ 稀疏（BM25），各自召回候选
  → ② 结果融合：RRF 等方式合成统一候选池
  → ③ 神经重排序：跨编码器对 Top-N 精排
  → 最终 Top-N
```

### 阶段一：并行检索

系统同时向稠密和稀疏两个引擎发送查询，各自召回一部分候选文档。

示例（查询 `kitty behavior`）：

```text
稠密检索（语义匹配 kitty ≈ cat）        稀疏检索（精确匹配 "kitty"）
  doc3: "feline habits and cat play…" cos=0.87    doc5: "kitty litter training…" BM25=8.4
  doc7: "cat grooming patterns…"     cos=0.82    doc9: "kitty adoption guide…"  BM25=6.1
  doc1: "pet care basics…"           cos=0.71    doc2: "kitten health tips…"    BM25=3.2
```

两路各自的排序都合理，但侧重点不同——这正是需要融合的原因。

### 阶段二：结果融合（RRF）

**难点**：两路得分不可直接比较。稠密的余弦相似度通常是 0-1，BM25 可能是 0 到几十的任意值，尺度与分布完全不同。

**倒数排名融合（Reciprocal Rank Fusion, RRF）**：完全抛开原始得分、只看排名。

\[
\text{score} = \sum \frac{1}{k + \text{rank}}
\]

- `k` 是平滑常数，**常取 60**，用于压低排名最靠前几个位置之间的得分差距。
- 优点：简单且稳健，不需要归一化两路得分。
- 缺点：**只利用了排名信息，丢失了原始得分中蕴含的丰富相关性信号**。

### 阶段三：神经重排序（Neural Reranking）

**重要澄清**：重排序**并不是为了「补救 RRF 丢掉的得分」才存在的**。无论前一步用哪种融合方式，**重排序都值得加**，因为它换用了一种**更强的匹配范式**。

| | 双编码器（Bi-Encoder） | 跨编码器（Cross-Encoder） |
| --- | --- | --- |
| 做法 | 查询和文档**各自独立**编码成向量，靠向量运算比相似度 | 查询和候选文档**拼接**成一段完整文字送入模型，逐词比对后输出综合相关性得分 |
| 速度 | 极快 | 慢得多 |
| 精度 | 无法捕捉深层匹配关系 | 判断更准确 |
| 角色 | 从海量数据做初步筛选 | 对候选池精排 |
| 常用模型 | 句向量模型（如 BGE-M3 稠密输出） | 如 `BAAI/bge-reranker-v2-m3` |

**打个比方**：求职者把简历交给猎头快速筛选，是双编码器；面试官与每位候选人深谈，是跨编码器。

**重排序不替代融合**：融合负责从两路结果中产生统一的候选池，重排序负责在这个候选池上精排。二者分工不同。

**工程参数**：通常只对融合产生的候选池中**排名靠前的 N 个**（如前 50 个）逐一精确打分。

## 2. 如何度量检索质量

调优多阶段流水线需要客观指标。三个核心指标（均在**带标注答案**的测试查询集上计算）：

| 指标 | 直觉解释 | 回答的问题 |
| --- | --- | --- |
| **recall@k（召回率 @k）** | 包含正确答案的文档出现在前 k 个结果中的查询比例 | 「该找的找到了吗」——**最贴近 RAG 需求**：只要相关文档进入上下文，LLM 就有机会利用它 |
| **MRR（平均倒数排名）** | 每个查询取第一个相关文档排名的倒数，再对所有查询取平均 | 「找到得够不够靠前」——排第 1 得 1 分，排第 10 只得 0.1 分 |
| **nDCG（归一化折损累积增益）** | 综合考虑所有相关文档的排名与相关程度，越靠后折扣越大 | 「整个排序列表的质量如何」 |

工业界还常见**检索失败率**：正确信息未出现在 top-20 检索结果中的查询比例。

**调到什么程度算够**：以 recall@k 为主目标（RAG 场景下漏召回比重排序更致命），MRR 与 nDCG 作为排序质量的补充；失败率用于监控长尾。

## 3. 按查询类型拆解指标

不同查询类型对稠密/稀疏的依赖不同，必须分开度量：

| 查询类型 | 例子 | 优势路 |
| --- | --- | --- |
| 语义相似 | `kitty` → `feline` / `cat` | 稠密 |
| 精确名称 | 人名、产品型号、错误码 | 稀疏 |
| 多语言 | 中文查询命中英文文档 | 多语言稠密模型 |
| 技术代码 | `HTTP-403`、`NullPointerException` | 稀疏 |

没有哪种单一检索策略在所有场景下都可靠。**把稠密、稀疏和重排序组合起来，才是构建生产级 RAG 系统的正确做法。**

## 4. 观察重排序的价值

有效的验证方式：记录每个文档在**原始稠密排名、原始稀疏排名、重排序后排名**三者的变化。通过分析「排名变化」数据，可以清晰看到重排序器如何把**被单一方法低估但实际高度相关**的文档提升到顶端。

## 5. 自检

- [ ] 融合用 RRF（k=60）或其他可解释方式，未直接相加原始得分
- [ ] 重排序范围已限定（Top-N），延迟可接受
- [ ] 理解重排序与融合的分工，未用前者替代后者
- [ ] 有带标注的查询集，以 recall@k 为主指标
- [ ] 指标按查询类型（语义/精确/多语言/代码）拆解
- [ ] 记录了重排序前后的排名变化，验证其收益
