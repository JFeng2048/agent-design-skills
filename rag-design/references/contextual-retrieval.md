# 上下文感知检索：修补分块环节

前面几篇都在分块之上**加结构**（树、图、链接、Agent 循环）。回过头看，最基础的分块环节本身也有一个**固有缺陷**需要修补。

---

## 1. 缺陷：分块切断了片段与原始上下文的联系

无论用哪种切分策略，都会留下这些问题：

- 「该公司收入增长了 3%」——**哪家公司**？哪个季度？
- 这段话出自**哪份报告**、哪个章节？
- 表格的表头在上一块，数据在这一块。

结果：**脱离上下文的块，其嵌入向量本身就无法精确表达含义**——模型和检索器都只能看到一段语义模糊的文本。

---

## 2. 思路：给每个块补一段「我是谁、出自哪里」

**上下文感知检索（Contextual Retrieval）** 的做法：

```text
原始块（语义模糊）          →  原块 + 上下文说明（再嵌入/索引）
"该公司收入增长了 3%"           "本文档是 ACME 2024 Q3 财报。
                                本节为「营收分析」章节。
                                ACME 2024 Q3 收入同比增长 3%。"
```

要点：

1. **用 LLM 为每个块生成一段定位说明**（这段内容属于哪份文档、哪个章节、讲什么主题、与相邻块的关系）；
2. 把该说明**拼接在块内容之前**，再送入嵌入模型建索引、并同样用于 BM25；
3. 检索返回时仍可保留原始块（避免上下文说明污染最终给模型的内容，或按需一起返回）。

**本质**：这不是在检索器上打补丁，而是**提升每个分块自身的检索质量**——让块的语义完整，检索才可能准。

---

## 3. 与其他技术的关系与顺序

| 技术 | 作用层 | 解决的问题 |
| --- | --- | --- |
| **上下文感知检索** | **分块**（最底层） | 块自身语义不完整 |
| 混合检索 + 重排 | 检索 | 两路盲区互补 + 精排 |
| 配额分配 | 候选池 | 名额如何在文档间分配 |
| 结构化索引（RAPTOR/图） | 索引组织 | 跨文档关联与多层次导航 |
| Agentic RAG | 流程 | 迭代探索 |

**顺序建议：先修分块，再加结构。** 块自身质量差时，上层结构建立在一堆语义模糊的碎片上，事倍功半。

---

## 4. 代价与替代方案

### 代价

- 每个块都要额外一次 LLM 调用生成上下文说明（**成本随块数线性增长**）；
- 索引体积增大（说明 + 原文）。

### 轻量替代方案（成本敏感时优先）

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| **标题路径前缀** | 块前加 `文档名 > 章节 > 小节` | 结构化文档，零 LLM 成本 |
| **元数据带出处** | 块带 source/version/章节元数据，注入上下文时展示 | 只需答案可追溯 |
| **表格整块保留** | 表头与数据不分离 | 表格类内容 |
| **指代替换** | 块内把指代词替换为实体名 | 规则可覆盖的场景 |

**先用轻量方案拿到大部分收益，再对高价值知识库补 LLM 生成上下文说明。**

---

## 5. 验收

| 指标 | 期望 |
| --- | --- |
| recall@k | 提升（尤其指代密集、跨章节引用的文档） |
| 检索失败率 | 下降 |
| 答案可追溯性 | 提升（有明确出处） |

用 `assets/evaluation_plan_template.md` 记录前后对比；用 `scripts/chunk_inspector.py` 检查块是否还带标题路径与元数据。
