# 知识组织：文件系统范式（OpenViking）

RAPTOR 与 GraphRAG 代表学术界的探索；**OpenViking（字节跳动火山引擎开源）提出第三种哲学：文件系统范式**——不把上下文视为扁平向量碎片或图谱节点，而是把所有上下文（记忆、资源、技能）映射为虚拟文件系统中的目录和文件。

---

## 1. 虚拟 URI：统一寻址

```text
viking://
├── resources/          # 外部知识：文档、代码库、网页
├── user/memories/      # 用户记忆：偏好、习惯
└── agent/
    ├── skills/         # Agent 自身：技能
    └── memories/       # Agent 自身：经验
```

`viking://` 是**虚拟 URI**——形式上类似 `http://` / `file://`，但不指向具体物理位置。Agent 用统一路径与 URI 引用知识，框架在背后决定从内存、磁盘还是远程加载。

---

## 2. 核心设计：L0/L1/L2 三层按需加载

资源写入时，系统自动把原始内容提炼为三个抽象层次：

| 层 | 内容 | 约 token | 用途 |
| --- | --- | --- | --- |
| **L0** | 一句话摘要（`.abstract`） | ~100 | 快速判断目录相关性 |
| **L1** | 核心信息与使用场景（`.overview`） | ~2,000 | 供 Agent 规划决策 |
| **L2** | 完整原始内容 | 全量 | 仅在需要深入时按需加载 |

每个目录下自动生成 `.abstract` 与 `.overview` 文件，形成从根到叶的层次化摘要结构。

**收益**：若 L0 层即判定无关，则无需加载 L1/L2；大部分查询加载到 L1 即可完成决策，**Token 消耗大幅降低**。

这套「摘要常驻、按需取全文」的思路与 **Skills 的渐进式披露**如出一辙：先让 Agent 只看到轻量元信息，确有需要时再逐层拉取完整内容，把 Token 花在刀刃上。

---

## 3. 为什么选 Markdown 纯文本而非专用数据库

看似反直觉，实为深思熟虑：

| 收益 | 说明 |
| --- | --- |
| 可读可改 | 用户可直接阅读、编辑和修正 Agent 的知识 |
| 版本控制 | 可通过 Git 版本控制与回滚 |
| Agent 可自主写入 | Agent 拥有 `write_file` 能力后，可在工作分支上自主记录和组织知识，再经审核流程合入主库 |

会话结束时，系统可提议把用户偏好更新写入 `user/memories/`、把操作记录写入 `agent/memories/`。

**关键区分**：`user/memories/` 属于**用户知识管理**；`agent/memories/` 中的操作记录只有经过结果评价、跨轨迹归纳和后续验证，才会成为**经验学习**，而不是把任意一次操作直接当成可靠经验。

## 4. 极易被忽视的前提：文件之间必须建立链接

`.abstract/.overview` 解决的是**纵向的层次摘要**；这里强调**横向的关联**。

**问题**：如果只是把知识拆成一批各自独立的文本文件平铺在目录里、彼此没有交叉引用，那么除了逐个全文扫描或向量检索之外，Agent 几乎无从在相关条目间导航——**知识越多，这堆零散文件反而越难检索**。

**正确做法：把知识库组织得像 Wikipedia**：

- 每个条目在提及其他条目时都以**链接**指向它；
- 辅以**入口页与索引页**；
- Agent 能顺着链接从一个概念走到相关概念。

这相当于用轻量的文件链接，实现了 GraphRAG 实体关系图谱的一部分导航能力。

### 模型不会自动做这件事

实践中有一个关键差异：**不同模型主动建立链接的意愿与能力并不相同**。能力强的模型在写入新知识时会自发回指已有条目、顺手维护索引；而不少模型只是孤立地追加文件。

因此**负责写入知识的提示词里必须把要求写明确**：

1. 每新增一个条目，先**检索**相关的已有条目；
2. 建立**双向可达**的引用（新条目链接到旧条目，旧条目/索引页也回指新条目）；
3. 更新所在**目录的索引页**；
4. 不允许知识退化成互不相连的孤岛。

可用 `scripts/knowledge_link_check.py` 把这条纪律固化为检查。

---

## 5. 与其它组织方式的取舍

| 方式 | 适合 | 代价 |
| --- | --- | --- |
| 扁平分块 + 混合检索 | 「找到包含某信息的片段」 | 无额外索引成本 |
| RAPTOR 树 | 多层次导航、概念到细节 | 聚类 + 摘要的 LLM 调用 |
| GraphRAG 图 | 多跳推理、实体消歧 | 实体/关系提取 + 社区发现的 LLM 调用 |
| 文件系统范式（L0/L1/L2 + 链接） | 知识需要被**人类与 Agent 共同维护**、可版本控制、可审计 | 需人工/AI 持续维护链接与索引 |

**组合建议**：文件系统范式可作为**骨架**（人可读、可 Git），L0/L1 承担层次摘要，链接承担横向导航，向量/BM25 承担内容检索，GraphRAG 作为多跳场景的专项索引。

---

## 6. 自检

- [ ] 知识有统一寻址（URI 或等价路径约定）
- [ ] 有 L0/L1（或等价的两级摘要），L0 即可判断相关性
- [ ] 核心知识以 Markdown 纯文本保存，可读、可 Git、可回滚
- [ ] 每个条目在提及其他条目时以链接指向
- [ ] 有入口页与目录索引页，并随新增条目更新
- [ ] 写入提示词明确了「先检索已有条目 → 建双向链接 → 更新索引」
- [ ] 用 `knowledge_link_check.py` 检查过孤岛文件与断链
- [ ] Agent 自身经验与用户知识分开存放，且经验需经评价才升级
