# 知识更新：增量更新与全量整理

只更新不整理，内容会越积越乱；只做定期重写，新信息又无法及时生效。**完整的更新机制必须同时包含两条路径**：

```text
事件触发 → 增量更新（局部，及时）
周期触发 → 全量整理（全局，去重/去旧/合并）
```

---

## 1. 增量更新：把知识库当成代码库

**最稳妥的工程答案：把每次知识变更当成一个 Pull Request（PR）。**

这不只适用于 User as Code 这类 Python 形式的可执行记忆；**Markdown 知识库、用户记忆文件和规则文档同样应当进入 Git**，获得差异审查、版本历史、责任追溯和一键回滚能力。

**生产环境不应让任何一个模型绕过审核，直接改主分支或线上向量库。**

---

## 2. 提议者—审核者闭环

沿用「Proposer — Reviewer」模式，把知识更新做成**有外部证据的迭代闭环**：

```
1. Proposer Agent 提交 PR
   从原始证据中发现新事实、冲突或过期内容 → 工作分支上提出「尽可能小而完整」的 diff
   （不是把最新一次对话粗暴追加到文件末尾，而是先检索相关已有知识，再增/删/改，
     同步维护链接、索引、时间元数据和证据引用）
        ↓
2. Reviewer Agent 独立审核
   拿到：变更前的知识 + diff + 原始证据（execution trajectory / 原始对话 / 业务文档 / 工具执行结果）
   检查：新断言是否被证据支持、是否遗漏限定条件、是否与其他文件冲突、删除或改写是否过度
        ↓ 不通过 → 返回「指向具体证据和行号」的可执行意见
3. 双方迭代至收敛
   Proposer 按拒绝理由修改 diff，Reviewer 回到原始证据复核
   【必须】设置最大迭代次数或成本预算；超出上限仍未收敛 → 转人工审核，绝不默认放行
        ↓ 批准
4. 合入后再发布
   CI 检查格式、链接、元数据、权限标签；知识以代码表示时还要跑类型检查和测试
   通过后从已合入版本增量重建受影响的分块、摘要和向量索引
```

**关键结论：索引是可重建的派生物，Git 中已审核的知识才是真正的来源。**

---

## 3. 三层分离

| 层 | 内容 | 可变性 |
| --- | --- | --- |
| **原始证据层** | 只增不改的对话、轨迹、原始文档 | append-only |
| **知识层** | 经过提炼、可持续修订的 Markdown 或代码 | 可修订（经 PR） |
| **服务层** | 从特定已合入版本生成的检索索引 | 可重建 |

PR 需记录：证据标识、知识库版本、审核意见、最终决定——使线上每条知识都能回答「**从哪条证据而来、谁在什么时候批准**」。

---

## 4. 为什么必须是 Agent，而不是两次固定 LLM 调用

知识更新不是对一段预先挑好的文本做摘要：

- **Proposer** 往往要主动搜索其他相关的知识文档和规则；
- **Reviewer** 要追溯证据、对比多份文档、运行检查，发现新线索时继续查询。

这需要它们拥有**文件搜索、版本比较、测试执行和证据检索**工具，现成的 Coding Agent 通常就能胜任。

两个 Agent 都应能按需查询**完整的知识库和原始证据库**，而不是只接收上游挑选的几个片段——注意「完整」指其**被授权的租户或用户范围**，不能因审核而突破隐私边界。

为保证可追溯性，两者的工作轨迹、工具输出引用和审核反馈也应以文本归档。

---

## 5. 异源互审

**两个 Agent 应优先使用能力相近但来自不同家族的模型**：

- Proposer 用 Claude，Reviewer 用 GPT；
- 或 Proposer 用 DeepSeek，Reviewer 用 Kimi。

| 为什么异源 | 为什么能力相近 |
| --- | --- |
| 不同训练数据、偏好和推理习惯，降低两者在同一处犯同类错误的概率 | 能力悬殊时 Reviewer 可能根本跟不上 Proposer 对复杂证据的处理 |

**边界**：异源能增加独立性，但**不能替代原始证据**——Reviewer 应主要核对证据和 diff，而不是沿着 Proposer 的结论再讲一遍。

**权限强制分工**：

| 角色 | 权限 |
| --- | --- |
| Proposer | 只能写**工作分支** |
| Reviewer | **只读**证据，只提交审核结果 |
| 合并流程 | 唯一能更新主分支和线上索引的环节 |

---

## 6. 全量整理：定期重审

增量更新的优点是及时，但每次只看局部。长期运行后，多次局部正确的修改仍可能累积出全局问题：同一事实散落多处、新旧说法并存、摘要偏离原始证据、目录结构不适配当前规模。

可理解为「睡眠学习」在知识管理中的实现：前台交互持续累积，后台周期性从全局视角重审整个知识体系。

### 三项核心工作

**1. 去重、去旧与合并**

全量扫描，识别语义重复、已被取代、过度碎片化或只有表述差异的条目，删除、归并或重写；重新建立文件间链接、入口页和索引页；必要时拆分过大文件、合并过小文件或调整目录层次。

> 这里删除的是**可服务的知识表达**，不是下层只增不改的**原始证据**。

**2. 回到原始数据核查**

不能只在已有摘要之间相互改写，否则早期的遗漏和误读会一代代传下去。整理 Agent 需逐段对照原始对话、execution trajectory、业务文档和工具输出，检查旧摘要是否：
- 遗漏关键事实
- 丢失否定词或时间条件
- 把推测错当成了事实

对大型知识库可按目录、时间或主题**分批扫描**，但必须保留**覆盖清单**，确保分批最终覆盖全量，而不是随机抽样。

**3. 冲突解决与场景限定（qualification）**

遇到互相矛盾的说法时，**不应简单「保留最新一条」或让模型猜哪条正确**。要追溯各自的原始信息源，检查它们是否分别在不同时间、对象、地域、任务或前置条件下成立：

- 两者都有效 → **不是删除其中一条，而是把各自的适用场景明确写入知识**；
- 证据仍不足 → **保留冲突和待确认状态**，不得强行收敛成一个确定结论。

### 产物不直接覆盖主库

全量整理同样由 Proposer 在分支上提交重组 diff，再由异源 Reviewer 审核。diff 较大时可按目录或主题拆成多个 PR，但应**共享同一份整理计划和覆盖清单**。

全部 PR 通过后：除重建全量派生索引，还应**回放一组典型检索与问答用例**，确认新结构没有让原本可找到的知识变得不可见。

**触发条件**：按时间（每周/每月），或在新增条目数、冲突数、检索质量下降超过阈值时触发。

## 7. 失效内容检测与下线

一篇被新版取代的旧政策若仍留在库中，检索时可能与新版一起被召回，让模型给出自相矛盾甚至过时的答案。

**做法**：给每个分块附加**版本号、生效/失效时间**等元数据：

- 检索阶段**过滤掉已失效内容**；或
- 提炼摘要时显式标注「此条已于某日废止」。

这与用户记忆里的**版本化冲突检测**是同一思路，只是搬到了共享知识库的尺度。

---

## 8. 多用户共享：权限与租户隔离

「所有用户共享」不等于「所有内容对所有人可见」。不同部门、租户、权限等级的用户能看到的文档范围往往不同。

**关键原则：检索必须按调用者的权限过滤，绝不能让越权文档进入某个用户的上下文。**

- **把权限过滤下推到检索层尤其重要**：一旦敏感内容进入 LLM 上下文，就很难保证它不以某种形式泄露到最终回答；
- 多租户系统还需保证租户之间的**向量索引和元数据相互隔离**，避免一个租户的查询「串味」检索到另一个租户的私有知识。

可直接填写 `assets/knowledge_update_policy.md`：触发条件、PR 流程与预算、整理周期、失效下线规则、权限过滤位置。

## 10. 自检

- [ ] 知识库已纳入 Git（含 Markdown 知识文件）
- [ ] 每次变更走 PR，没有模型能直接改主库/线上索引
- [ ] Proposer 与 Reviewer 异源、能力相近，权限分工明确
- [ ] 审核意见指向具体证据和行号，不模糊
- [ ] 设置了最大迭代/预算，超出转人工，不默认放行
- [ ] 分块带版本与生效/失效时间，检索层过滤失效内容
- [ ] 检索层按调用者权限过滤；租户索引与元数据隔离
- [ ] 定期整理包含回原始数据核查，保留覆盖清单
- [ ] 冲突保留场景限定，未强行收敛
- [ ] 结构化变更后回放了典型检索用例，确认知识未变不可见
