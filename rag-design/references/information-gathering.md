# 自主调研：能自己查到的，不要问用户

核心原则：**Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

## 1. 四种调研手段

| 手段 | 能拿到什么 | 做法 |
| --- | --- | --- |
| 项目勘察 | 向量库与索引类型、嵌入模型、分块配置、是否有 BM25 与重排序、查询日志 | `python scripts/discover_rag_context.py <项目目录>` + 定向检索（见第 2 节） |
| 文档与检索 | 嵌入模型维度与长度上限、ANN 索引特性与版本差异、重排序模型、基准结论 | 用 `web_search` / `web_fetch` 查权威来源，**不要凭记忆给结论** |
| 线上数据 | 真实查询分布、低召回/低精度的查询类型、点击与反馈 | 读查询日志，按查询类型分类归因 |
| 实测 | recall@k / MRR / nDCG、分块质量、延迟与成本 | 跑标注集 + `scripts/retrieval_eval.py` + 对照实验 |

判定顺序：**先项目 → 再文档/检索 → 再线上数据与实测 → 仍不确定且属业务决策，才问用户。**

## 2. 项目勘察清单

| 目标 | 检索方式 |
| --- | --- |
| 向量库与索引类型 | `grep -rn "chroma\|faiss\|qdrant\|milvus\|weaviate\|pgvector\|pinecone\|annoy\|hnsw"` |
| 嵌入模型 | `grep -rn "embedding_model\|SentenceTransformer\|bge-\|text-embedding\|embed_query"` |
| 分块配置 | `grep -rn "chunk_size\|chunk_overlap\|RecursiveCharacterTextSplitter\|split_text"` |
| 稀疏检索 | `grep -rn "bm25\|BM25\|tfidf\|inverted_index\|rank_bm25"` |
| 重排序 | `grep -rn "rerank\|cross_encoder\|CrossEncoder\|bge-reranker"` |
| 检索入口 | `grep -rn "similarity_search\|retrieve\|top_k\|retriever"` |
| 相似度度量 | `grep -rn "cosine\|inner_product\|l2\|metric="` |
| 查询日志 | `find . -name "*.jsonl"`、日志目录 |

自动化：`python scripts/discover_rag_context.py <项目目录>`，输出带 `文件:行` 证据的事实与推断的默认方案（区分**代码命中**与**仅在文档中提及**）。

## 3. 从线上数据倒推设计缺口

检索失效案例是最有价值的设计输入：

| 失效现象 | 可能的缺口 |
| --- | --- |
| 语义相似查询召不回 | 缺稠密路，或嵌入模型不支持目标语言 |
| 错误码/人名查不到 | 缺 BM25 稀疏路，或被分词切碎 |
| 命中但排在很后面 | 缺重排序；或融合方式不当 |
| 命中块内容不完整 | 块太小，或切分切断了指代 |
| 命中块噪声大 | 块太大，一个块多个主题 |
| 新文档检索不到 | 索引不支持增量（用了 ANNOY 类），或重建周期过长 |
| 长文档内容检索不到 | 嵌入模型输入长度受限，长文本被截断 |

## 4. 能从项目里直接推断的结论

| 调研发现 | 推断 |
| --- | --- |
| 只有向量检索、无 BM25 | 补稀疏路（精确查询短板） |
| 索引为 ANNOY 类但文档频繁更新 | 换 HNSW 或规划定期重建 |
| chunk_size 过大（> 2000） | 拆分，先降块大小再测 recall@k |
| 无重排序 | 加跨编码器对 Top-N 精排（收益通常最直接） |
| 两路得分直接加权相加 | 改 RRF 或做归一化 |
| 中文文档用空格分词 | 改中文分词或二元组，否则索引质量差 |
| 无任何标注集 | 先建 30-50 条标注查询，再谈调优 |

## 5. 什么才必须问用户（业务决策）

只有这几类：**查不到、且属于人的取舍**：

1. **知识范围与更新频率**：哪些文档入库、多久更新一次（决定索引选型）。
2. **成本与延迟的权重**：是否上重排序、ANN 索引的内存预算。
3. **精度与召回的取舍**：宁可多召回让 LLM 筛选，还是严格控制噪声。
4. **数据边界**：哪些文档可入库、是否需要按权限过滤检索结果。

提问要求：
- 一次 **≤3 个问题**，每个给 **2-4 个选项**，**标明推荐项与推荐理由**（依据来自哪个文件 / 哪次实测）。
- 绝不问能从项目或文档里读到的信息（用了什么向量库、现有块大小等）。
- 用户说「你定」或不回复 → 采用推荐项，在 `assets/requirements_intake.md` 记为**假设**并注明复核时间。

## 6. 常见坑

- **凭记忆给模型能力**：维度、长度上限、是否支持多语言以官方文档为准。
- **没有标注集就调参**：改了参数说不清变好还是变坏。
- **只调块大小不换策略**：结构化文档用固定大小硬切，调参收益有限。
- **把重排序当万金油**：候选池本身有偏时，精排救不回来。
- **一次性问一堆开放问题**：用户还得自己去查，答案质量更差。
