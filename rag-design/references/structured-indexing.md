# 结构化索引：从信息检索到知识建模

混合检索解决的是「给定一个文本块，如何找到最相关的那几个」。但更根本的问题是：**这些文本块本身该怎么组织**。把文档切成互不关联的扁平文本块，会丢掉知识固有的层次和跨文档关联。

**核心思路：在索引之前先用 LLM 把知识整理一遍——归纳、抽象、建立关联。** 多花索引阶段的计算，换取更好的检索质量。

---

## 1. 为什么必须提炼：两个失败案例

### 案例一：黑猫白猫的计数问题

知识库有 100 个独立案例文档（90 只黑猫、10 只白猫），用户问「比例是多少」。受限于 top-k（如 20），大部分案例根本检索不到，模型只基于不完整样本（如 15 黑 3 白）得出错误结论。

**解法**：预先生成摘要「共有 100 只猫：90 只黑猫（90%）和 10 只白猫（10%）」并索引，**一次检索即可获得准确信息**。

### 案例二：Xfinity 优惠资格的边界问题

几百条客服工单各自记录一个个案结论（退伍军人 John 通过、医生 Sarah 拿到折扣、教师 Mike 被告知不符合），没有任何一条写着资格范围本身。护士来问「我能不能享受优惠」时有三重障碍：

| 障碍 | 说明 | 能否靠调参解决 |
| --- | --- | --- |
| 最近邻偏置 | 「护士」与「医生」语义最近，Sarah 排最前 → 推断护士可以；若 Mike 排更前则结论相反 | 不能根治，需结构 |
| 边界语义缺失 | 「仅限…，其他一律不适用」这种全称/否定边界**不存在于任何单条工单中** | 调大 k 也解决不了 |
| 完整性信号缺失 | 模型无从判断是否看全，于是不追问，照着手里几条自信作答 | 需要主动补全 |

**解法**：离线通读整个工单库，提炼出一条**规则卡**——「Xfinity 优惠适用于现役与退伍军人、持证医护人员（含护士）；教师等其他职业不适用」。

**两个案例的共同结论**：把原始案例或文档不加处理地直接放进知识库远远不够。未经提炼和结构化的知识，无论塞进向量库、注入上下文还是塞进长上下文，模型都无法可靠利用。**必须在索引阶段投入计算资源，主动提炼、抽象和结构化。**

## 2. RAPTOR：树状层次索引

**RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）** 采用自下而上的递归抽象：

```text
全局摘要            ← 根节点
聚类摘要 A B C      ← 中间层
文本块 1..7         ← 叶子层
原始文档
```

构建过程：

1. 长文档切分为小文本块作为**叶子节点**；
2. 用**聚类算法**把语义相近的叶子分组（如同把图书馆的书按主题自动分堆）；
3. 用 LLM 为每组生成更高层次的摘要作为**父节点**；
4. 递归直至形成一棵从具体细节（叶子）到高度概括（根）的知识树。

**收益**：检索可在多个抽象层次进行——既精确回答细节问题，也提供宏观理解。例：关于 SSE 指令的多个叶子（「SSE2 支持 128 位整数运算」「SSE4.1 新增字符串比较指令」）聚类到一组，生成父节点摘要「x86 SIMD 指令集的各代演进」。

**检索路径**：**跨层穿梭**——先在较高层摘要定位宏观概念，再沿树向下钻取到叶子细节。适合「从概念逐步钻进细节」的查询。

## 3. GraphRAG：实体-关系知识图谱

将文档建模为**实体（Entities）与关系（Relationships）构成的图谱**，知识以三元组（主语-关系-宾语）表达，如（北京, 是首都, 中国）。大量三元组交织成知识之网。

流程：LLM 提取关键实体 → 提取实体间关系 → 用**社区发现（Community Detection）**算法找出语义紧密的实体集群并生成摘要，形成思维导图。

### 两个核心优势

**1. 多跳关系推理**（最不可替代的能力）

问「我的医生所在医院的地址」需依次解析「用户 → 医生 → 医院 → 地址」。扁平存储中这类查询要么多次独立检索再由 LLM 拼接（效率低且易断链），要么根本无法表达；图结构天然支持沿关系边遍历。

**2. 实体消歧**（Entity Disambiguation）

注意与**词义消歧**（Word Sense Disambiguation）的区别：

| | 词义消歧 | 实体消歧 |
| --- | --- | --- |
| 例子 | `bank` 指河岸还是银行 | 两个同名的「张医生」 |
| 靠什么 | 上下文感知的嵌入即可解决 | 需维护关于**实体本身**的知识 |
| 落在哪 | 嵌入模型（见 `dense-embedding.md`） | 结构化字段（见 `multi-document-quota.md` 之外的存储格式） |

在图中，（张医生-A, 科室, 牙科）与（张医生-B, 科室, 心脏科）是不同节点，各自的关系边天然区分，**消歧成为图结构的原生能力，无需额外推理**。

**检索路径**：在「关系网」中漫游——定位「SSE」实体，遍历关系边找到「XMM 寄存器」「浮点运算」及具体指令（如 ADDPS），并通过所在社区获得其在 CPU 架构中的位置上下文。适合「谁和谁有关？A 如何影响 B？」。

## 4. RAPTOR vs GraphRAG：解决不同问题

| | RAPTOR | GraphRAG |
| --- | --- | --- |
| 结构 | 树（层次） | 图（关系） |
| 擅长 | 从概念逐步钻进细节 | A 和 B 之间是什么关系 |
| 典型查询 | 「从整体架构到具体指令的逐步深入」 | 「SSE 与 AVX 在架构上有什么区别」 |
| 检索路径 | 跨层穿梭 | 关系网漫游 |

**生产场景里组合使用通常比单选一种效果更好。**（注：选型时以官方当前版本为准，记忆类框架的图能力也可能演变为「实体链接仅用于检索加权」。）

## 5. 什么时候值得投入结构化索引

**判断标准**：

| 查询形态 | 建议 |
| --- | --- |
| 「找到包含某信息的文档片段」（如「退款政策是什么」） | 混合检索就够了 |
| 经常需要**跨文档综合**（如「SSE 与 AVX 在架构上的区别」） | 值得结构化索引 |
| 需要**多层次导航**（从整体架构到具体指令） | 值得结构化索引（RAPTOR） |
| 需要**多跳推理**或**同名实体精确区分**（医疗问诊、法律案件、家族关系） | 值得结构化索引（GraphRAG） |

**代价**：索引构建与查询都需要更多次 LLM 调用，**成本和延迟都显著增加**。

---

## 6. 知识图谱作为记忆的局限（重要提醒）

将自然语言转为三元组**不可避免地导致语义降级**：

> 「如果下周还下雨，我就取消去海边的计划，改成去博物馆」
> → 被分解为（我, 有计划, 海滩旅行）与（我, 有备选计划, 博物馆旅行）
> → **条件逻辑和时间依赖全部丢失**

此外，三元组提取的准确性高度依赖 LLM 理解能力，错误提取会导致**知识污染**。

**分层互补的推荐策略**：

1. 以**完整自然语言保存核心信息**（保留语义完整性）；
2. 辅以**结构化元数据做索引和检索**（兼顾查询效率）；
3. 在需要多跳推理和精确消歧的**垂直场景**，将知识图谱作为**专项索引手段**，与自然语言记忆协同工作。
