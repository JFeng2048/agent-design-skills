# 文档分块（Chunking）

查询时的流程是检索、增强、生成；但在能检索之前，还有一步不可或缺的**离线预处理**——把长文档切成适合独立检索的片段（chunk）。

## 1. 为什么必须分块

两个原因：

1. **嵌入模型有输入长度限制**；且一整篇文档只压缩成一个向量时，多个主题混在一起，向量无法精确表达任何一个——这与记忆系统里 Enhanced Notes 遇到的问题同源：**段落越长，嵌入越难抓住重点**。
2. **检索的目标是只把相关的那部分注入上下文**。片段太大会连带引入大量无关内容，浪费窗口、稀释注意力。

## 2. 三类分块策略

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **固定大小切分** | 按固定 token 数（如 512）切分，相邻块保留 50-100 token 重叠 | 实现简单、结果可预测 | 完全无视文档结构，段落/代码/表格可能被拦腰截断 |
| **递归/结构感知切分** | 按自然边界（章节标题、段落、句子）递归切分；先试大边界，仍超长再降级到更小边界 | 尊重文档结构；Markdown、HTML 等有显式结构的文档尤其适合 | 需要按文档类型配置边界规则 |
| **语义切分** | 计算相邻句子的嵌入相似度，在语义「断崖」（相似度骤降处）下刀 | 块内主题单一，切分质量最高 | 需要额外的嵌入计算，成本高 |

**目前生产系统最常用的默认是递归/结构感知切分。**

## 3. 块大小与重叠的权衡

| 方向 | 问题 |
| --- | --- |
| 块太小 | 单块信息不完整，脱离上下文后语义模糊：「该公司收入增长了 3%」——哪家公司？哪个季度？ |
| 块太大 | 一个块混杂多个主题，嵌入向量被稀释，检索精度下降；命中后还会带入更多无关内容 |

**实践起点**：每块 **256-1024 token**，相邻块重叠 **10%-20%**，再根据检索质量实测调优。

重叠的作用是避免关键句子恰好在边界处被切断。重叠太少起不到保护作用，太多则造成冗余与存储浪费。

## 4. 分块的固有缺陷（重要伏笔）

无论采用哪种策略，分块都会**切断片段与其原始上下文的联系**：

- 「该公司」指代谁？
- 这段话出自哪份报告、哪个章节？
- 表格的表头在上一块，数据在这一块。

这些信息留在了块的外面。这是分块的固有缺陷，需要靠**上下文感知检索**（为每个块补充文档级上下文，如在块前加标题路径、文档名、章节摘要）来正面解决。

**工程补偿办法**（在上下文感知检索之前也可先用）：

- 每块保留**标题路径**（如 `产品手册 > 退款政策 > 七天无理由`）。
- 每块带**文档级元数据**（来源、版本、更新时间、权限标签）。
- 表格与代码块**整块保留**，不做切分。
- 指代消解：块内把指代词替换为实体名（可由规则或小模型完成）。

## 5. 分块配置的决策表

| 文档类型 | 推荐策略 | 边界规则 | 备注 |
| --- | --- | --- | --- |
| Markdown / HTML | 递归/结构感知 | `#` `##` 标题 → 段落 → 句子 | 标题路径写入元数据 |
| 代码仓库 | 结构感知 | 文件 → 函数/类 → 行块 | 保留文件路径与符号名 |
| PDF / 扫描件 | 固定大小 + 重叠 | 先做版面解析再切 | 注意表格与多栏排版 |
| 表格密集型文档 | 整表不切 | 表为单位 | 超长表再按行分组并带表头 |
| 对话/日志 | 按会话或时间窗 | session_id / 时间 | 保留参与者与时间戳 |
| 法律/规约文本 | 结构感知 | 条 → 款 → 项 | 保留条款编号，便于引用 |

## 6. 体检与调优

用 `scripts/chunk_inspector.py` 检查已生成的块：

- 块大小分布（是否集中在目标区间）
- 实际重叠率（是否达到设定值）
- 是否有过小块（信息不完整）与超大块（主题混杂）
- 是否切断了 Markdown 标题、代码块、表格等结构边界

调优顺序：**先改策略与边界规则，再调块大小与重叠**，每一步都用 recall@k 验证。

## 7. 自检

- [ ] 按文档类型选了策略，结构化文档未用固定大小硬切
- [ ] 块大小与重叠在推荐区间，且有实测依据
- [ ] 每块带标题路径与文档级元数据
- [ ] 表格与代码块未被拦腰截断
- [ ] 已识别指代与出处丢失问题并有补偿措施
