# 记忆的层次结构：存在哪里

设计记忆系统可拆成三个独立维度——**放哪里、怎么存、存什么**。本节回答「放哪里」。

## 1. 三层划分

| 层次 | 作用域 | 可变性 | 用途 |
| --- | --- | --- | --- |
| 轨迹（Trajectory） | 单次会话 | append-only（只增不改） | 为当前决策提供即时上下文，可追溯、调试、审计 |
| 用户长期记忆 | 跨会话、跨实例 | 反复改写、合并、淘汰 | 个性化与连续性 |
| 业务状态 | 任务级 | 随任务推进变更 | 表示任务逻辑阶段（事件驱动架构中尤为重要） |

本章聚焦**轨迹**与**用户长期记忆**两个核心层次。分层设计既保证 Agent 高效处理当前任务（依赖轨迹），又具备长期个性化能力（依赖长期记忆）。

## 2. 轨迹（Trajectory）

一次 Agent 运行过程中的完整历史记录——用户消息 + 模型回复 + 工具执行结果，按时间顺序排列，**只增不改**：新事件不断追加到末尾，已写入的记录不被修改或删除（append-only）。

要点澄清：
- 「只增不改」描述的是**用于追溯、调试或审计的原始事件记录**。
- 为控制长度，**每轮实际发送给模型的运行时 Context** 可以经过压缩、重组，或用摘要替换部分历史。
- 原始记录是否完整保留，取决于具体系统的**数据保留与审计要求**。

轨迹回答的是：「我刚才说了什么」「用户如何回应」「工具返回了什么结果」。

## 3. 用户长期记忆

跨会话、跨实例的持久化存储，通常以**键值对形式与特定用户 ID 绑定**，存储偏好设置、历史交互摘要和提取的知识点。Agent 通过**特定工具调用**显式读取和更新长期记忆，实现跨会话的个性化和连续性。

对比：**轨迹是流水账，长期记忆是档案。**

| 维度 | 轨迹 | 用户长期记忆 |
| --- | --- | --- |
| 时间跨度 | 单次会话 | 跨会话、跨实例 |
| 写入方式 | 顺序追加，不可变 | 显式工具调用改写、合并、淘汰 |
| 内容粒度 | 原始事件全量 | 提炼后的事实与知识 |
| 主要用途 | 当前决策、审计 | 个性化、连续性 |
| 增长 | 每轮必然增长 | 受压缩与淘汰控制 |

## 4. 业务状态

开发者定义的**高层状态抽象**，表示任务的逻辑阶段，例如：

```text
需要澄清 → 处理请求中 → 等待付款 → 请求完成
```

这类抽象在**事件驱动的 Agent 架构**中尤为重要。它不是用户事实，而是任务进度；与 `agent-status-design` 中的状态栏是同一类关注点。

## 5. 工作记忆与轨迹的关系

认知科学把记忆划分为工作记忆与长期记忆，引入 Agent 后需要厘清两个易混概念：

- **工作记忆**（Working Memory）：对应 Agent 的**上下文窗口**——处理当前任务的临时信息空间。轨迹是其中**最核心**的内容，但工作记忆还可能包含**从长期记忆中激活加载**的信息。
- **轨迹**：不可变的完整事件序列（按时间追加）。

两者都为当前决策提供即时上下文，区别在于：

| 维度 | 轨迹 | 工作记忆 |
| --- | --- | --- |
| 是否可变 | 不可变，按时间追加 | 经过筛选与激活的动态子集 |
| 组织依据 | 时间顺序 | 相关性裁剪 |
| 内容来源 | 本会话原始事件 | 原始事件 + 长期记忆激活 |

**动态交互**：重要信息**选择性转移**到长期记忆；相关长期记忆被**激活加载**进工作记忆。

## 6. 层次划分的设计决策

| 决策点 | 判断依据 |
| --- | --- |
| 是否需要业务状态层 | 是否有明确的任务阶段与事件驱动流转 |
| 轨迹保留多久、是否完整 | 审计与合规要求；调试需要 |
| 运行时 Context 如何裁剪 | 上下文预算、任务类型；与 `agent-status-design` 的压缩策略联动 |
| 长期记忆的键设计 | 用户 ID 绑定 + 类别命名空间（见 `storage-formats.md`） |
| 激活加载策略 | 哪些长期记忆需要在会话开始时进入工作记忆 |

## 7. 自检

- [ ] 轨迹与长期记忆边界清晰，轨迹为 append-only
- [ ] 运行时 Context 的裁剪策略已定义，未破坏原始记录
- [ ] 长期记忆与用户 ID 绑定，读写走显式工具调用
- [ ] 若有多阶段任务，业务状态层已定义且阶段可枚举
- [ ] 长期记忆到工作记忆的激活策略已定义
- [ ] 保留期限满足审计与合规要求
