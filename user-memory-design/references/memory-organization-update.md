# 记忆的组织与更新：从扁平存储到可维护的知识库

前几篇解决「怎么存、怎么取、怎么缩」。本回答另外两个问题：**记忆文件之间怎么组织**，以及**新证据到来后怎么改、怎么定期整理**。

---

## 1. 组织范式：文件系统式（OpenViking 风格）

把用户记忆组织成**虚拟文件系统**，统一 URI 寻址：

```text
viking://
├── resources/          # 外部知识（与 user-memory-design 的 RAG 部分衔接）
├── user/memories/      # 用户记忆：偏好、习惯、事件
└── agent/memories/     # Agent 自身经验（需经评价才升级）
```

### L0/L1/L2 三层按需加载

| 层 | 内容 | 约 token | 用途 |
| --- | --- | --- | --- |
| L0 | 一句话摘要 | ~100 | 快速判断目录相关性 |
| L1 | 核心信息与使用场景 | ~2,000 | 供 Agent 规划决策 |
| L2 | 完整原始内容 | 全量 | 仅在需要深入时加载 |

**收益**：大部分查询在 L0/L1 即可完成决策，Token 消耗大幅降低——与 Skills 的渐进式披露同源。

### 为什么用 Markdown 纯文本

| 收益 | 说明 |
| --- | --- |
| 可读可改 | 用户可直接阅读、编辑和修正 Agent 的记忆 |
| 可版本控制 | Git 差异审查、版本历史、一键回滚 |
| Agent 可自主写入 | 在有 `write_file` 能力后可在工作分支记录，再经审核合入 |

**关键区分**：`user/memories/` 是用户知识管理；`agent/memories/` 的**操作记录只有经过结果评价、跨轨迹归纳和后续验证，才会成为经验学习**，而不是把任意一次操作直接当成可靠经验。

## 2. 必须维护的横向链接

层次摘要解决**纵向**（从叶到根）；**横向**关联靠链接。

**问题**：若记忆被拆成一批各自独立的文件、彼此无交叉引用，则除了全文扫描或向量检索外几乎无法导航——**记忆越多越难检索**。

**做法（像 Wikipedia）**：每个条目提及其他条目时以链接指向，并维护入口页与索引页。

**实践警告**：不同模型主动建链接的意愿与能力不同，不少模型只会孤立追加文件。因此**写入记忆的提示词必须明确要求**：

1. 新增条目前先**检索**相关已有条目；
2. 建立**双向可达**引用；
3. 更新所在目录的**索引页**。

这条纪律可用链接检查脚本固化为自动检查（参考 `rag-design` 的 `knowledge_link_check.py`：孤岛、断链、索引覆盖）。

## 3. 增量更新：把记忆变更当 Pull Request

把知识库/记忆当**代码库**管理，每次变更是 PR。

```text
1. Proposer Agent 提交 PR
   从原始证据（对话、轨迹、工具结果）中发现新事实/冲突/过期内容
   → 工作分支上提出尽可能小而完整的 diff
   → 先检索相关已有记忆，再增/删/改，同步维护链接、索引、时间元数据、证据引用
        ↓
2. Reviewer Agent 独立审核
   拿到：变更前的记忆 + diff + 原始证据
   检查：新断言是否被证据支持、是否遗漏限定条件、是否与其他文件冲突、删除/改写是否过度
        ↓ 不通过 → 返回指向具体证据和行号的可执行意见
3. 迭代至收敛（必须设最大迭代/预算，超出转人工，绝不默认放行）
        ↓ 批准
4. CI 检查格式/链接/元数据 → 增量重建受影响索引
```

**两层权限分工**：Proposer 只能写工作分支；Reviewer 只读证据；只有合并流程能更新主记忆库。

**异源互审**：两个 Agent 用能力相近但不同家族的模型（如 Proposer 用 Claude、Reviewer 用 GPT），降低在同一处犯同类错误的概率。但异源**不能替代原始证据**——Reviewer 应核对证据与 diff，而不是顺着结论复述。

## 4. 定期整理（睡眠学习）

增量更新每次只看局部；长期运行后同一事实散落多处、新旧说法并存、摘要偏离原始证据。需要**周期性全量整理**：

| 工作 | 要点 |
| --- | --- |
| 去重、去旧与合并 | 识别语义重复、已被取代、过度碎片化的条目；重建链接与索引；删除的是**可服务的记忆表达**，不是只增不改的原始证据 |
| 回原始数据核查 | 检查旧摘要是否遗漏关键事实、丢失否定词或时间条件、把推测当成事实；**必须保留覆盖清单**，确保覆盖全量而非随机抽样 |
| 冲突解决与场景限定 | 不简单「保留最新」；追溯各自原始信息源，若都有效则**把各自适用场景写入记忆**；证据不足则**保留冲突和待确认状态**，不强行收敛 |

整理产物同样走 PR 分支 + 异源审核；合并后应**回放一组典型检索问答用例**，确认新结构没有让原本可找到的记忆变不可见。

---

## 5. 失效与权限

| 项 | 规则 |
| --- | --- |
| 失效下线 | 记忆带版本号、生效/失效时间；检索层过滤已失效内容，避免新旧矛盾同时被召回 |
| 权限边界 | Proposer/Reviewer 只能访问**其被授权的用户范围**，审核不突破隐私边界 |
| 投毒防护 | 记忆内容若来自可被外部污染的数据源（网页、邮件），即是被注入面；来源标记 + 高风险动作确认（见 `references/information-gathering.md` 的失效案例表） |

---

## 6. 三层分离

| 层 | 内容 | 可变性 |
| --- | --- | --- |
| 原始证据层 | 对话、轨迹 | append-only |
| 记忆层 | 提炼后的偏好、事件、知识 | 经 PR 修订 |
| 服务层 | 索引、摘要、缓存 | 可重建 |

**索引是可重建的派生物，已审核的记忆才是唯一来源。**

---

## 7. 自检

- [ ] 记忆有统一寻址与目录结构，区分 `user/memories/` 与 `agent/memories/`
- [ ] 有 L0/L1 层次摘要，常驻轻量、按需取全文
- [ ] 核心记忆用 Markdown 保存，可读、可 Git、可回滚
- [ ] 记忆条目之间有链接，排除了孤岛与断链
- [ ] 写入提示词明确要求「先检索已有 → 建双向链接 → 更新索引页」
- [ ] 记忆变更走 PR，Proposer/Reviewer 异源且权限分工
- [ ] 迭代有最大次数/预算，超出转人工
- [ ] 定期整理含回原始数据核查与覆盖清单
- [ ] 冲突写场景限定，未强行收敛
- [ ] 记忆带版本与生效时间，失效内容在检索层被过滤
- [ ] Agent 经验经评价后才升级，未把单次操作直接当经验
