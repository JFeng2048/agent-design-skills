# 自主调研：能自己查到的，不要问用户

核心原则：**Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

## 1. 四种调研手段

| 手段 | 能拿到什么 | 怎么做 |
| --- | --- | --- |
| 项目勘察 | 是否已有记忆实现、存储后端、提取与检索方式、PII 处理、记忆条目形态 | `python scripts/discover_memory_context.py <项目目录>` + 定向检索（见第 2 节） |
| 文档与检索 | 框架能力边界与版本差异（如 Mem0 v2/v3）、向量库选型、合规要求 | 用 `web_search` / `web_fetch` 查权威来源，**不要凭记忆给结论** |
| 线上数据 | 真实查询分布、记忆命中率、失效案例（该记住没记住 / 记错了） | 读日志与评测样本，从失效案例倒推设计缺口 |
| 实测 | 三层次能力得分、检索延迟、存储增长曲线 | 跑评测集 + `scripts/memory_lint.py` + 对照实验 |

判定顺序：**先项目 → 再文档/检索 → 再线上数据与实测 → 仍不确定且属业务决策，才问用户。**

## 2. 项目勘察清单

| 目标 | 检索方式 |
| --- | --- |
| 是否已有记忆实现 | `grep -rn "mem0\|memobase\|Memory()\|long_term\|user_profile\|memory_store"` |
| 存储后端 | `grep -rn "redis\|sqlite\|postgres\|chroma\|faiss\|qdrant\|pinecone\|pgvector"` |
| 记忆提取逻辑 | `grep -rn "extract\|summarize\|memory_update\|write_memory"` |
| 检索方式 | `grep -rn "embedding\|bm25\|vector_search\|hybrid\|rerank"` |
| PII 与脱敏 | `grep -rn "pii\|sanitize\|redact\|mask\|脱敏"` |
| 记忆 schema | `grep -rn "class Memory\|memory_schema\|Profile\|backstory"` |
| 用户标识绑定 | `grep -rn "user_id\|uid\b"` |
| 日志与轨迹 | `find . -name "*.jsonl"`、日志目录 |

自动化：`python scripts/discover_memory_context.py <项目目录>`，输出带 `文件:行` 证据的事实与推断的默认方案（区分**代码命中**与**仅在文档中提及**）。

脚本**只遍历源码与文档**，默认跳过与记忆设计无关的文件：构建产物与依赖（`dist/ build/ out/ target/ node_modules/ __pycache__/ .venv/ vendor/` 等）、编译产物与二进制（`*.pyc *.so *.class *.jar *.wasm` 等）、压缩打包（`*.min.js *.bundle.js *.map`）、锁文件（`package-lock.json` `yarn.lock` `poetry.lock` 等）、生成代码（文件头含 `Code generated by` / `DO NOT EDIT` / `@generated`）。可用 `--exclude`（路径子串）、`--max-file-size`（KB，默认 300）、`--max-line`（默认 1000，跳过压缩后的长行）调整。

## 3. 从线上数据倒推设计缺口

失效案例是最有价值的设计输入：

| 失效现象 | 可能的缺口 |
| --- | --- |
| 该记住的没记住 | 提取规则缺少选择性之外的抽象化；或类别未覆盖 |
| 记住了但检索不到 | 检索信号单一（只有语义），缺实体或时间维度 |
| 同名实体混淆（张医生是谁的医生） | 缺 backstory / person / relationship 消歧字段 |
| 旧信息被当成当前事实 | 缺时间戳或未在检索时按时间排序 |
| 矛盾信息导致行为摇摆 | 写入策略未定（覆盖 vs 并存），或检索未做冲突裁决 |
| 记忆库膨胀、检索变慢 | 缺压缩与淘汰；重复记忆未聚类 |
| 涉及敏感信息的投诉 | 脱敏位置不对或未覆盖自然语言类 PII |

## 4. 能从项目里直接推断的结论

| 调研发现 | 推断 |
| --- | --- |
| 已有向量库且 recall 尚可 | 复用现有检索，补 BM25 / 实体 / 时间信号 |
| 记忆条目无时间戳 | 必须补，否则无法按时间取当前事实 |
| 已有 user_id 绑定 | 记忆键设计沿用现有命名空间 |
| 日志含明文手机号/身份证 | 脱敏优先级最高，且须本地完成 |
| 记忆条目为纯文本长段 | 属 Enhanced Notes，量大时应拆分或分级 |
| 已有 profile 槽位配置 | 按 Memobase 式画像组织，槽位由开发者控制 |
| 查询多为「上次是什么时候」 | 需要情景记忆的多维元数据检索 |

## 5. 什么才必须问用户（业务决策）

只有这几类：**查不到、且属于人的取舍**：

1. **记忆范围与保留期限**：哪些能存、存多久、是否允许跨用户聚合。
2. **一致性与历史的取舍**：矛盾信息覆盖（库简洁）还是并存（保留历史）。
3. **合规与权限边界**：谁能读、能否导出、能否删除（遗忘权）。
4. **成本与效果权重**：每次会话提取的调用预算、延迟上限。

提问要求：
- 一次 **≤3 个问题**，每个给 **2-4 个选项**，**标明推荐项与推荐理由**（依据来自哪个文件 / 哪次实测）。
- 绝不问能从项目或文档里读到的信息（框架版本、存储后端、现有限制等）。
- 用户说「你定」或不回复 → 采用推荐项，在 `assets/requirements_intake.md` 记为**假设**并注明复核时间。

## 6. 常见坑

- **凭记忆判断框架能力**：Mem0 v2/v3 差异极大，版本结论必须来自官方迁移指南。
- **只看写入不看检索**：很多问题出在检索信号单一，而非记忆没存进去。
- **忽略时间戳**：没有时间戳的记忆无法处理「现在住在哪」这类问题。
- **把压缩阈值拍脑袋定**：用脚本按真实分布测算。
- **一次性问一堆开放问题**：用户还得自己去查，答案质量反而更差。
