# 用户记忆的四种存储格式：怎么存

同一条用户信息，可以用不同的粒度和结构来表示。四种格式代表**记忆粒度与结构复杂度的递进**：简单性递减、表达力递增。

## 1. 四种格式对比

| 格式 | 形态 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Simple Notes | `用户邮箱：john@x.com` | 原子事实 · O(1) · 开销极低 | 关联性丢失 |
| Enhanced Notes | `在 TechCorp 任高级工程师，带 5 人推荐团队…` | 整段叙事 · 语义完整 | 冗余 · 难更新 · 长文难检索 |
| JSON Cards | `work.position.title = …`（类别→子类别→键值） | 三层结构化 · 支持部分更新 | 刚性分类 |
| Advanced JSON Cards | + backstory + person + relationship + 时间戳 | 消歧 · 知识管理 · 带来源与关系 | 生成维护成本高 |

## 2. Simple Notes

每条记忆是一个**最小的、不可再分的事实**。

```text
用户邮箱：john@example.com
用户在 TechCorp 工作
用户职位是高级工程师
用户负责推荐系统开发
```

- 优势：开销极低，支持 O(1) 操作（耗时固定、不随数据量增长）。
- 劣势：**信息关联性完全丢失**——同一份工作的内在联系被割裂成三条独立事实。处理需要综合多条信息才能回答的查询时，系统需要重新拼凑碎片。

## 3. Enhanced Notes

每条记忆保存为**包含完整上下文的段落**。

```text
用户在 TechCorp 担任高级软件工程师，专注于机器学习已有三年，
目前领导一个推荐系统项目，团队 5 人。
```

- 优势：保留叙事结构，语义完整丰富。
- 代价：存储冗余（相同信息在多个段落中重复）、更新复杂（属性变化需重写多个段落）、长文难检索。

## 4. JSON Cards

采用**三层嵌套结构**（类别 → 子类别 → 键值对），模拟人类对信息的分类方式。

```json
{
  "personal": { "contact": { "email": "john@example.com" } },
  "work": {
    "company": { "name": "TechCorp" },
    "position": { "title": "高级软件工程师", "team_size": 5 }
  }
}
```

- 优势：支持**部分更新**（改 `work.position.title` 不影响 `work.company.name`），可预测且可扩展。
- 劣势：**刚性结构**假设信息可清晰分类——「周末用 Python 开发个人项目」同时涉及时间偏好、技术偏好和活动类型，强制归入单一类别会丢失多维性。

## 5. Advanced JSON Cards

从**信息存储**到**知识管理**的范式转变。每张卡片除事实外，还加入：

| 字段 | 作用 | 回答的问题 |
| --- | --- | --- |
| `backstory` | 信息获取的背景叙事 | **为什么**存这条信息 |
| `person` | 主体身份 | **为谁**存 |
| `relationship` | 与用户的关系 | 这条信息和用户什么关系 |
| `timestamp` | 时间戳 | 什么时候的、是否仍是当前事实 |

核心思想：**同一条信息在不同场景下可能有完全不同的含义**——「张医生」可能是用户自己的牙科医生，也可能是用户父亲的心脏科医生，脱离具体情境就无法正确理解。

解决的是**消歧问题**：现实中用户可能有多个身份（为自己、为父母、为子女），简单键值存储无法准确区分。

```json
{
  "person": "父亲",
  "relationship": "家庭成员",
  "fact": "心脏科医生：张医生",
  "backstory": "用户提到父亲去年做了心脏支架手术，主治医生姓张",
  "timestamp": "2025-03-12"
}
```

当用户说「帮我安排家人的年度体检」时，系统可通过 `relationship` 识别所有家庭成员，通过 `backstory` 了解健康历史。

代价：生成和维护成本较高。

## 6. 选择标准

| 数据特征 | 推荐格式 | 理由 |
| --- | --- | --- |
| 关键且少量（偏好、关键人物关系） | Advanced JSON Cards | 保证可检索性与消歧能力 |
| 大量且非关键（对话事实） | Simple Notes | 降低成本 |
| 需要叙事完整性但不常更新 | Enhanced Notes | 语义完整 |
| 需要部分更新且分类清晰 | JSON Cards | 结构化 + 可维护 |

**多数生产系统采用混合模式**——同一 Agent 内不同类别的信息走不同路径。

## 7. 实验观察

在统一接口下实现四种模式（各提供记忆生成与检索），在三层次评估集上测试：

- **Simple Notes** 以最低生成成本通过第一层「基础回忆」的多数用例，但在需要综合多条信息、区分同名实体的**第二、三层用例上频繁失分**。
- **Advanced JSON Cards** 在涉及**消歧和跨会话关联**的用例上表现最好，代价是每次会话结束后的记忆维护调用**明显更贵、更慢**。

实践建议：亲手切换四种模式，对比同一个测试用例生成的记忆文件——差异在具体例子面前一目了然。

## 8. 与检索的关系

- Simple Notes 依赖**检索时拼凑**，检索压力大。
- Enhanced Notes 长文**难检索**，适合小量高价值记忆。
- JSON Cards 可按**类别路径**精确取用，支持部分更新。
- Advanced JSON Cards 的 `person` / `relationship` 字段是**多维检索的索引**（见 `evaluation-framework.md` 第二层）。
