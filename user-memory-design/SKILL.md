# 用户记忆系统设计（编码实现指导）

要让 Agent 跨会话提供个性化服务，需要一层**持久的用户记忆**。它不保存每句对话，而是用额外的 LLM 调用**提取、压缩并审查**对未来有用的事实——这与只在当前窗口生效的上下文学习不同。

**本 skill 的定位是编码实现指导，不是提示词模板**：产出是记忆系统的数据结构、写入与检索管线、压缩与脱敏机制的设计与实现方案，载体是代码，不是一段写死的提示词。

## 动手前：自己把需求调研清楚，尽量不问用户

**核心原则：Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

### 1. 自主调研（项目 → 文档 → 线上数据）

| 手段 | 能拿到什么 | 做法 |
| --- | --- | --- |
| 项目勘察 | 是否已有记忆实现、存储后端、提取与检索方式、PII 处理、记忆条目形态 | `python scripts/discover_memory_context.py <项目目录>` + 定向检索（见 `references/information-gathering.md`） |
| 文档与检索 | 框架（Mem0 / Memobase 等）能力边界与版本差异、向量库选型、合规要求 | 用 `web_search` / `web_fetch` 查权威来源，**不要凭记忆给结论** |
| 线上数据 | 真实查询分布、记忆命中率、失效案例（该记住没记住/记错了） | 读日志与评测样本，从失效案例倒推设计缺口 |
| 实测 | 三层次能力得分、检索延迟、存储增长曲线 | 跑评测集 + `scripts/memory_lint.py` + 对照实验 |

判定顺序：**先项目 → 再文档/检索 → 再线上数据与实测 → 仍不确定且属业务决策，才问用户。**

### 2. 推断默认方案（可直接落地）

- 层次划分：默认「轨迹（append-only）+ 用户长期记忆」两层；有明确任务阶段再引入业务状态。
- 存储格式：默认**混合模式**——关键且少量（偏好、关键人物关系）用 Advanced JSON Cards，大量非关键对话事实用 Simple Notes。
- 写入策略：默认**仅追加（ADD-only）+ 检索时按时间与相关性排序**，避免错误 UPDATE/DELETE 不可逆丢历史。
- 检索：默认**混合检索**（语义 + BM25 + 实体 + 时间）取 Top-k。
- 压缩：默认三层（重要性评分 → 聚类摘要 → 抽象泛化），阈值由 `scripts/importance_scoring.py` 测算。
- 隐私：默认**本地小模型**做 PII 检测与脱敏，日志不出本机。

### 3. 只有业务决策才问用户

必须问的只有这几类（查不到、且属于人的取舍）：

1. **记忆范围与保留期限**：哪些能存、存多久、是否允许跨用户聚合。
2. **一致性与历史的取舍**：矛盾信息是覆盖（库简洁）还是并存（保留历史）。
3. **合规与权限边界**：谁能读、能否导出、能否删除（遗忘权）。
4. **成本与效果权重**：每次会话的提取调用预算、延迟上限。

提问要求：一次 **≤3 个问题**，每个给 2-4 个选项，**标明推荐项与推荐理由**；用户说「你定」→ 采用推荐项并记为假设，写入 `assets/requirements_intake.md`。

## 三套正交的分类体系（贯穿全部设计决策）

| 分类体系 | 回答的问题 | 类别 |
| --- | --- | --- |
| **记忆层次** | 存在哪里？ | 轨迹（当前会话）、用户长期记忆（跨会话）、业务状态（任务阶段） |
| **存储格式** | 怎么存？ | Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards（进阶：User as Code） |
| **认知类型** | 存什么？ | 情景记忆（具体事件）、语义记忆（一般知识）、程序记忆（行为流程） |

三者**正交、可自由组合**：一条「用户偏好靠窗座位」的语义记忆，可以用 Simple Notes 存在长期记忆里；一段「先搜直飞 → 确认座位 → 用常旅客号」的程序记忆，可以用 Advanced JSON Cards 存储。

- 选**哪种格式**取决于工程需求（简单性 vs 表达力）。
- 选**存什么类型**取决于业务场景（要记住事实、事件还是流程）。
- 详见 `references/memory-hierarchy.md`、`references/storage-formats.md`、`references/memory-types.md`。

## 设计流程（按序执行）

### 1. 确立评估标准
产出：三层次评估集 + 八项能力中的重点关注项。
- **第一层 基础回忆**：准确存储与检索用户直接提供的、结构化、无歧义的信息（如「我的会员号是 12345」）。
- **第二层 多会话检索**：跨时间、跨对象检索出全部相关信息并推理（如两辆车时主动询问为哪辆保养）。
- **第三层 主动服务**：综合多会话甚至很久以前的信息，提供预见性帮助（如订国际航班时预警护照即将过期）。
- 八项能力：个人信息保留、偏好追踪、上下文切换、记忆更新、多会话连续性、复杂思考、时间感知、冲突解决。
- 详见 `references/evaluation-framework.md`，评测计划模板见 `assets/evaluation_plan_template.md`。

### 2. 划分记忆层次
产出：轨迹 / 长期记忆 / 业务状态的边界与交互方式。
- **轨迹**：单次会话的完整原始记录，按时间追加、**只增不改**（append-only），用于追溯与调试。运行时 Context 可压缩或摘要，但原始记录是否保留取决于审计要求。
- **用户长期记忆**：跨会话持久化存储，通常键值对 + 用户 ID 绑定，会被反复改写、合并、淘汰。
- **业务状态**：开发者定义的高层阶段（需要澄清 / 处理中 / 等待付款 / 完成），事件驱动架构中尤为重要。
- 轨迹是**流水账**，长期记忆是**档案**。详见 `references/memory-hierarchy.md`。

### 3. 确定存什么：提取规则
产出：提取提示与结构化 schema。
- 提取结果必须同时满足三条规则：
  - **选择性**：丢弃「搜索返回 3 个选项」这类短期细节。
  - **抽象化**：把本次「靠窗座位」归纳为长期偏好，而非某次航班的座位号。
  - **结构化**：用可检索的字段保存事实。
- 按认知类型分类存储：情景（事件）/ 语义（稳定特征）/ 程序（可复用流程）。
- 详见 `references/memory-types.md`。

### 4. 确定怎么存：格式选型
产出：按类别划分的格式方案（多为混合模式）。
- Simple Notes：原子事实、开销极低、O(1)，但关联性丢失。
- Enhanced Notes：整段叙事、语义完整，但冗余、难更新、长文难检索。
- JSON Cards：类别 → 子类别 → 键值三层，支持部分更新，但分类刚性。
- Advanced JSON Cards：额外带 backstory（为什么存）、person（为谁存）、relationship（与用户关系）、时间戳，解决消歧，但生成维护成本高。
- 选择标准：**关键且少量** → Advanced JSON Cards；**大量且非关键** → Simple Notes；多数生产系统为混合模式。
- 详见 `references/storage-formats.md`，schema 见 `assets/memory_schema_template.md`。

### 5. 确定写入策略
产出：写入管线（提取 → 决策 → 落库）。
- **写入时消歧**（Mem0 v2 路线）：LLM 抽取候选事实 → 向量检索相近记忆 → LLM 判定 ADD/UPDATE/DELETE/NOOP。库始终简洁一致；风险是一次错误更新会**不可逆丢失历史**，且每条候选都要检索 + 二次 LLM 判断。
- **仅追加 + 检索时推理**（Mem0 v3 路线）：一次 LLM 抽取、只做 ADD，带时间信息的事实并存；查询时融合语义、BM25、实体与时间信号排序。保留历史、减少 LLM 调用。
- 默认推荐后者。详见 `references/frameworks.md`。

### 6. 确定检索策略
产出：检索管线与排序信号。
- 混合检索：语义相似度 + BM25 关键词 + 实体匹配 + 时间信息，融合后取 Top-k。
- 时间感知是记忆检索的关键差异点：「现在住在哪」要取最新的，而非最相似的。
- 记忆量大时才需要独立检索层；量小时直接全量注入也可行。

### 7. 确定压缩与淘汰
产出：三层压缩策略与阈值。
1. **重要性评分**：访问频率 + 时间衰减 + 情感强度 + 信息独特性，低于阈值标记可压缩/删除。
2. **聚类**：相似记忆分组，每组生成代表性摘要，原始条目存档到二级存储。
3. **抽象泛化**：从具体情景记忆提取一般规律，转化为语义或程序记忆。
- 用 `scripts/importance_scoring.py` 测算阈值。详见 `references/compression-privacy.md`。

### 8. 确定隐私与脱敏
产出：PII 类型清单、脱敏位置与方式、保留策略。
- **本地小模型**做 PII 检测与脱敏（日志本身可能含敏感信息，发到云端脱敏违背初衷）。
- 覆盖结构化（身份证、银行卡）、半结构化（地址）、自然语言（「我的密码是 abc123」）。
- 高吞吐场景用混合策略：正则快速过滤 + LLM 深度分析剩余文本。
- 详见 `references/compression-privacy.md`，策略表见 `assets/privacy_policy_template.md`。

### 9. 验收
产出：三层次评测得分 + 对照结论。
- 每层各 20 个用例；第二、三层用例由多个跨时间跨对象的会话构成。
- 流程：按第一个会话生成记忆 → 仅凭记忆（不可回看原始对话）处理后续会话并更新记忆 → 用记忆回答新问题 → **LLM-as-a-judge** 与参考答案对比打分。
- 详见 `references/evaluation-framework.md`。

## 交付前自检清单

**调研与定位**

- [ ] 已自主调研项目并留下 `文件:行` 证据，未把可查到的信息抛给用户
- [ ] 框架能力与版本差异来自文档检索，非凭记忆
- [ ] 默认方案已给出且可直接落地（用户不选也能开工）
- [ ] 需要用户拍板的只剩业务决策，≤3 项且每项带选项与推荐项
- [ ] 交付物是代码实现方案，而非一份提示词模板

**层次与内容**

- [ ] 轨迹与长期记忆的边界清晰，轨迹为 append-only
- [ ] 提取规则满足选择性、抽象化、结构化三条
- [ ] 记忆按认知类型（情景/语义/程序）分类，且知道每类存什么
- [ ] 关键且少量的数据用了高表达力格式，大量非关键数据用低成本格式
- [ ] 涉及同名实体（多个家人、多辆车）的记忆带 backstory / person / relationship 可消歧

**写入与检索**

- [ ] 写入策略已明确（追加 vs 覆盖），并知道各自的历史丢失风险
- [ ] 每条记忆带时间戳，检索能按时间取当前事实
- [ ] 检索采用多信号融合（语义 + 关键词 + 实体 + 时间）
- [ ] 矛盾信息有明确处理路径（覆盖 或 时间排序）

**运维与合规**

- [ ] 有重要性评分与压缩阈值，且已用脚本测算
- [ ] 重复记忆会被聚类或去重
- [ ] PII 检测与脱敏在本地完成，日志不出本机
- [ ] 有保留期限、导出与删除（遗忘权）机制
- [ ] 记忆库质量经过 `scripts/memory_lint.py` 检查（无裸 PII、有来源与时间戳）

## 常见反模式

| 反模式 | 后果 | 修正 |
| --- | --- | --- |
| 把每句对话都存进记忆 | 记忆爆炸、检索噪声大 | 选择性提取，丢弃短期细节 |
| 只存原始事件不抽象 | 无法形成稳定偏好 | 抽象化为语义记忆 |
| 用 UPDATE/DELETE 覆盖矛盾信息 | 错误更新不可逆丢历史 | 改为仅追加 + 检索时时间排序 |
| 只做语义相似检索 | 「现在住在哪」取到旧值 | 融合时间信号排序 |
| 全用 Simple Notes | 同名实体无法消歧、需重新拼凑 | 关键数据升级为 Advanced JSON Cards |
| 全用 Advanced JSON Cards | 每次会话的维护调用又贵又慢 | 混合模式，按重要性分级 |
| 云端 API 做日志脱敏 | 敏感信息已外泄，违背初衷 | 本地小模型脱敏 |
| 不设保留期限与删除机制 | 合规风险（遗忘权） | 明确保留期限与删除路径 |
| 不查项目直接问用户一堆开放问题 | 用户还得自己去查 | 项目/文档/线上数据能拿到的自己拿 |
