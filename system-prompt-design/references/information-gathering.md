# 自主调研：能自己查到的，不要问用户

核心原则：**Agent 能力范围内能确认的事，自己确认。** 把问题推给用户没有意义——用户也得去查同样的资料。只有**必须由人拍板的业务决策**才需要用户参与，且必须给选项。

## 1. 四种调研手段

| 手段 | 能拿到什么 | 怎么做 |
| --- | --- | --- |
| 项目勘察 | 现有提示词与结构、工具定义与数量、业务规则与阈值实现、语言风格、是否已有 few-shot、动态字段风险 | `python scripts/discover_prompt_context.py <项目目录>` + 定向检索（见第 2 节） |
| 文档与检索 | 行业规范、平台差异、模型能力边界、同类产品做法 | 用 `web_search` / `web_fetch` 查权威来源，**不要凭记忆给结论** |
| 线上数据 | 真实失败案例、高频任务类型、用户投诉、运营经验 | 读日志与评测样本，**从失败案例倒推缺失的规则** |
| 实测 | 提示词是否生效、规则违反率、工具错误率 | 跑评测集 + `scripts/lint_prompt.py` + 对照实验（见 `ablation-experiments.md`） |

判定顺序：**先项目 → 再文档/检索 → 再线上数据与实测 → 仍不确定且属业务决策，才问用户。**

## 2. 项目勘察清单

| 目标 | 检索方式 |
| --- | --- |
| 现有提示词位置 | `grep -rn "SYSTEM_PROMPT\|system prompt\|system_prompt\|你是一个\|你是.*助手"` |
| 提示词文件 | `find . -name "*.prompt" -o -name "*prompt*.md"` |
| 工具定义与数量 | `grep -rn "\"name\".*\"description" --include=*.json`、`grep -rn "tools\s*="` |
| 业务规则实现 | `grep -rn "policy\|rule\|NEVER\|MUST\|上限\|阈值\|不得超过"` |
| 约束与阈值 | `grep -rn "max\|limit\|budget\|retry\|timeout"` |
| 是否已有 few-shot | `grep -rn "示例\|Example\|few_shot\|few-shot"` |
| 语言风格 | 统计提示词中 CJK 占比；看项目注释与文档语言 |
| 动态字段风险 | `grep -rn "datetime.now\|time.time\|当前时间" `（提示词里出现即为风险） |
| 模型与服务商 | `grep -rn "model\s*=\|claude-\|gpt-"` |
| 日志与评测样本 | `find . -name "*.jsonl"`、日志目录 |

自动化：`python scripts/discover_prompt_context.py <项目目录>`，输出带 `文件:行` 证据的事实与推断的默认方案（区分**代码/提示词命中**与**仅在文档中提及**）。

脚本**只遍历源码与文档**，默认跳过与提示词设计无关的文件：构建产物与依赖（`dist/ build/ out/ target/ node_modules/ __pycache__/ .venv/ vendor/` 等）、编译产物与二进制（`*.pyc *.so *.class *.jar *.wasm` 等）、压缩打包（`*.min.js *.bundle.js *.map`）、锁文件（`package-lock.json` `yarn.lock` `poetry.lock` 等）、生成代码（文件头含 `Code generated by` / `DO NOT EDIT` / `@generated`）。可用 `--exclude`（路径子串）、`--max-file-size`（KB，默认 300）、`--max-line`（默认 1000，跳过压缩后的长行）调整。

## 3. 从线上数据倒推规则（最有价值的来源）

规则不是拍脑袋写的，**从真实失败案例里长出来**：

1. 抽取线上失败会话（任务未完成、用户投诉、规则违反）。
2. 逐条归因：模型是**不知道规则**、**规则模糊**，还是**规则冲突时选错**？
3. 对应补：缺规则 → 新增；模糊 → 决策表 + 阈值；冲突 → 优先级条款。
4. 每条新规则做一次消融，确认收益（见 `ablation-experiments.md`）。

同时统计高频任务类型，把 SOP 优先写在高频路径上。

## 4. 能从项目里直接推断的结论

| 调研发现 | 推断 |
| --- | --- |
| 已有提示词且结构清晰 | 沿用现有块命名与顺序，只补缺失部分，避免风格漂移 |
| 工具数量 > 20 | 默认采用渐进式披露（`tool_search` / `defer_loading`） |
| 提示词中出现时间戳或用户 ID | 静态前缀被击穿，需移到 user 消息 |
| 规则中有“适当/酌情/尽量” | 该规则不可执行，需补枚举与阈值 |
| 项目文档为中文 | 提示词默认中文，术语沿用项目现有词汇 |
| 已有 few-shot 且内容重复度高 | 精简到 2-3 组覆盖边界 |
| 线上失败集中在某类任务 | 该类任务优先写完整 SOP |

## 5. 什么才必须问用户（业务决策）

只有这几类：**查不到、且属于人的取舍**：

1. **业务规则与判定口径**：某任务算哪一类、阈值多少、超限后拒绝还是降级。
2. **产品取舍**：转化率优先还是风控优先、是否允许 Agent 自主外联。
3. **权限与合规边界**：能读写什么、哪些数据不能进上下文。
4. **目标权重**：多指标冲突时以哪个为准。

提问要求：
- 一次 **≤3 个问题**，每个给 **2-4 个选项**，**标明推荐项与推荐理由**（依据写清来自哪个文件/哪次实测）。
- 绝不问能从项目或文档里读到的信息（工具数量、现有规则、模型名等）。
- 用户说“你定”或不回复 → 采用推荐项，在 `assets/requirements_intake.md` 记为**假设**并注明复核时间。

## 6. 常见坑

- **凭记忆下结论**：模型能力、平台差异以文档为准。
- **只看提示词不看代码**：业务规则的真实实现常在代码里，两边不一致时以代码为准。
- **把配置默认值当业务决策**：默认值 ≠ 业务规则，涉及规则才找产品确认（这是**确认**，不是**询问**）。
- **忽略线上数据**：凭空写的规则往往覆盖不到真正的失败模式。
- **一次性问一堆开放问题**：用户还得自己去查，答案质量反而更差。
