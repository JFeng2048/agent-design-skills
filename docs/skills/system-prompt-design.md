# system-prompt-design 设计说明

## 1. 它要解决的到底是什么

系统提示词工作的难点不是「写好几句话」，而是**把业务决策权从模型的自由裁量里收回到提示词中**。

这意味着真正的难点在两处：

1. **规则的可执行性**——模糊规则（「根据任务情况选择合适的计费类型」）会让同样的任务在不同时间得到不同分类。
2. **结构的认知负荷**——上百条零散规则没有流程图与优先级，模型会违反关键规则（消融实验里打乱结构导致成功率下降超 30%）。

所以这个 skill 不是教「怎么写提示词」，而是教**怎么把业务决策翻译成可执行的规则与流程，并验证它们的贡献**。

## 2. 主流程为什么是这 9 步

| 步骤 | 为什么放在这个位置 |
| --- | --- |
| 1 澄清身份与目标 | 先定边界，否则后面所有规则没有归属；失败姿态是语气约束的原料 |
| 2 定义语气与风格 | 越早定越好——它决定后续所有措辞的基调 |
| 3 搭建结构骨架 | 先有容器再填内容；Markdown 管层次、XML 管语义 |
| 4 把规则写成 SOP | 核心步骤：规则堆砌 → 带分支的流程 |
| 5 细化业务规则 | 把模糊处补成决策表与阈值（产品决策，工程只负责编码） |
| 6 决定 few-shot | 只在规则说不清时补，且要考虑缓存稳定性 |
| 7 设计工具定义 | 工具 schema 与提示词同属静态前缀，一并设计 |
| 8 加固提示注入 | 内容定稿后再做安全加固，否则反复返工 |
| 9 消融实验验收 | 最后验证每项内容的贡献 |

**顺序逻辑**：边界 → 风格 → 结构 → 内容 → 安全 → 验证。前一步是后一步的输入，颠倒会造成返工。

## 3. 为什么「新员工检验」是核心验收标准

设计一个检验标准比列一百条规范更有用。代入一位**聪明但完全不懂本业务的新员工**，只读这份提示词回答 5 个问题（我是谁 / 第一步做什么 / 规则冲突听谁的 / 绝对不能做什么 / 做错怎么交代）——**任何一条答不上来，Agent 在真实任务中同样答不上来**。

选它的原因：可操作（不需要跑实验就能自查）、覆盖全（五个问题分别对应身份、流程、优先级、禁止项、失败姿态）、且天然产出缺陷清单。

## 4. references 为什么拆成这 9 篇

每篇对应一个决策点：

| 文件 | 对应的决策 |
| --- | --- |
| `tone-and-persona.md` | 语气怎么定、大写强调用几处 |
| `structure-and-format.md` | 用 Markdown 还是 XML（答案是双层） |
| `sop-vs-rules.md` | 规则堆砌 vs 流程驱动的诊断与改写 |
| `business-rules.md` | 模糊规则怎么细化到可执行 |
| `few-shot.md` | 加不加示例、放哪、对缓存的影响 |
| `tool-design.md` | 工具描述写哪四类信息、如何渐进式披露 |
| `prompt-injection.md` | 三道上下文层防线怎么布 |
| `ablation-experiments.md` | 怎么验证每项内容的贡献 |
| `information-gathering.md` | 动手前从哪取信息 |

`information-gathering.md` 是后来补的——因为它解决的是「动手前先取事实」这个跨 skill 的共性问题。

## 5. 三个脚本的分工

| 脚本 | 为什么需要它 |
| --- | --- |
| `discover_prompt_context.py` | 自动从项目里取事实（现有提示词、工具、动态字段风险），避免把可查的信息抛给用户 |
| `lint_prompt.py` | 把「自检清单」里可机械判定的部分自动化：模糊措辞、强调密度、XML 配对、SOP 结构与分支、示例数量、安全要素、动态字段 |
| `check_prefix_stability.py` | 静态前缀必须**字节级稳定**，这是 KV Cache 命中的前提；人眼无法逐字节比对，必须脚本化 |

`check_prefix_stability.py` 支持**文件模式**（生成基线指纹）与**日志模式**（校验线上多次请求是否一致）——后者才能发现「按请求动态检索示例」「注入时间戳」这类真实问题。

## 6. 关键取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 规则 vs 流程 | 优先流程，规则做补充 | 流程让模型知道「现在在哪一步」，规则堆砌会丢失优先级 |
| 示例放系统提示词 vs 伪造成首轮对话 | 按会话类型是否变化决定 | 前者对所有请求生效，后者可按类型选示例集 |
| 大写强调 | 只留给真正关键的约束 | 过度使用会稀释注意力 |
| 业务规则谁定 | 产品定决策，工程做编码 | 工程师自行发明计费/权限逻辑是反模式 |

## 7. 与相邻 skill 的关系

- 提示词写**规则**（「每个商家最多拨打 3 次」）→ `agent-status-design` 由代码写出**事实**（「已拨打 3/3」）。
- 提示词里的**外部内容标记**是防注入的第一道防线 → 执行层防御在别的主题。
- 工具定义的**渐进式披露**与 `rag-design` 的检索思路同源：静态前缀只放简述，完整 schema 按需加载。
