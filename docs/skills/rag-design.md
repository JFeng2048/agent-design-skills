# rag-design 设计说明

## 1. 它要解决的到底是什么

构建共享知识库，把 LLM 的思考生成能力与外部知识库的广度、时效性结合——模型训练数据有截止日期，知识库可以随时更新。

流程是**检索 → 增强 → 生成**。但真正的工作全在检索侧，而且是一条**多阶段流水线**：分块 → 稠密/稀疏召回 → 融合 → 重排序 → 配额分配 → 注入。每个阶段都有独立的设计决策，这也是本 skill 步骤最多的原因。

## 2. 主流程为什么是这 8 步

| 步骤 | 为什么放在这个位置 |
| --- | --- |
| 1 先定度量 | **没有标注集与指标，后面所有调参都无法归因** |
| 2 文档分块 | 离线预处理，是检索质量的上游 |
| 3 稠密检索 | 语义路：模型 + ANN 索引选型 |
| 4 稀疏检索 | 关键词路：BM25 参数 |
| 5 混合与重排序 | 两路合并 + 精排 |
| 6 多文档配额分配 | 候选池 → 最终 Top-K 的名额分配 |
| 7 增强与生成 | 上下文注入 |
| 8 验收与调优 | 指标对照 + 消融 |

**第 1 步前置**是最关键的设计决定：检索系统的失败很难凭感觉定位（召不回 vs 排得后 vs 被霸屏），必须先有 recall@k / MRR / nDCG / 失败率，并按查询类型拆解，否则「调优」就是碰运气。

**第 6 步（配额分配）是后补的**。它解决的三个问题（单文档霸屏、硬性条数限制的副作用、名额浪费）在只做「重排后取 Top-K」的管线里必然出现，而且用硬限制防霸屏会引入新问题——所以它必须是独立的一步，而不是检索配置里的一个参数。

## 3. 为什么稠密与稀疏都要（而不是选一个）

两者的盲区互补且互不覆盖：

| 方法 | 盲区 | 例子 |
| --- | --- | --- |
| 稠密 | 懂语义但漏关键词 | 搜 `HTTP-403` 返回「服务器错误」的泛泛讨论 |
| 稀疏 | 精确但读不懂同义词 | 搜 `kitty` 找不到只写 `cat` 的文档 |

因此默认**两路并行 + 融合**。融合方式选 RRF（score = Σ 1/(k+rank)，k=60）的理由：两路得分尺度不同（余弦 0-1 vs BM25 任意正值），**不可直接相加**；RRF 只用排名，简单稳健。代价写清：丢失原始得分的相关性信号。

## 4. 为什么重排序不是「补救 RRF」

容易被误解为「RRF 丢了得分，所以用重排序补回来」。实际不是：**无论用什么融合方式，重排序都值得加**，因为它换用了更强的匹配范式。

| | 双编码器（检索阶段） | 跨编码器（重排序） |
| --- | --- | --- |
| 做法 | 查询与文档各自独立编码 | 拼接后逐词比对 |
| 速度/精度 | 快但浅 | 慢但准 |
| 角色 | 海量初筛 | 候选池精排 |

分工：**融合负责产生统一候选池，重排序负责在候选池上精排**——不互相替代。候选池本身有偏时，精排救不回来。

## 6. 五个脚本的分工

| 脚本 | 为什么需要它 |
| --- | --- |
| `discover_rag_context.py` | 勘察项目：向量库、嵌入模型、分块配置、是否有 BM25/重排序 |
| `chunk_inspector.py` | 分块质量：大小分布、实际重叠率、结构截断（围栏未闭合等） |
| `bm25_calc.py` | 输出 BM25 分步计算，用于校验实现与参数 |
| `retrieval_eval.py` | 指标必须算：recall@k / MRR / nDCG / 失败率，且按查询类型拆解 |
| `quota_allocator.py` | 配额分配器（最大余额法），含 α 敏感性扫描 |

两个实现细节值得记录：

- `bm25_calc.py` 的 `--idf-floor` 默认 0.0——DF > N/2 时 IDF 变负，必须设下限；脚本会真实暴露这个现象（「模型」命中 4/5 篇时 IDF 为负）。
- `quota_allocator.py` 补了三个工程细节：分数可能为负时平移为正（否则 `rel^α` 在小数 α 下无定义）、钳制后总名额偏离 K 的回补/回收、**缺口回填按小数余额最大者优先**。

## 7. 关键取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 分块策略 | 默认递归/结构感知切分 | 生产系统最常用的默认；Markdown/HTML 有显式结构 |
| 块大小 | 256-1024 token、重叠 10-20% 起步 | 太小语义模糊，太大向量被稀释；需实测调优 |
| 检索 | 混合（稠密 + 稀疏） | 单一策略在所有场景都不可靠 |
| 融合 | RRF（k=60） | 两路得分尺度不同，不可直接相加 |
| 重排序 | 对 Top-N（如前 50）精排 | 精度显著提升，但全量精排延迟与成本失控 |
| Top-K 取值 | 配额分配，不直接截断 | 直接截断会单文档霸屏 |
| 主指标 | recall@k | 最贴近 RAG 需求：相关文档进了上下文，LLM 才有机会用 |

## 8. 已知边界

- 配额分配**不解决文档内片段冗余**——那是 MMR / xQuAD 的职责，可叠加（配额管「文档间怎么分」，xQuAD 管「文档内选哪几条」）。
- 代表分用 `max` 聚合对「多片段平均相关」的文档有偏差，可改为 top-m 均值。
- 分块切断上下文（指代、出处）是固有缺陷，需要上下文感知检索来正面解决——本 skill 目前只给了工程补偿办法（标题路径、文档元数据、整表保留）。
