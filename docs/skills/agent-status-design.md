# agent-status-design 设计说明

## 1. 它要解决的到底是什么

不是「生成一段状态提示词」，而是**让 Agent 随时知道自己在哪、做了几次、还剩什么**。

根本原因在于注意力机制的一个性质：**上下文学习更像检索而非推理**。上下文窗口是一台只有一半的检索引擎——检索那一半很强（注意力能从成千上万 token 里捞出相关记录），但**缺了提炼层**：没有任何机制会自动数一遍、建个索引或就地总结。

于是「已经打了几次电话」这种结论，模型每次都得从原始记录里现算一遍，代价随上下文长度 N 增长，且错误率高。状态栏就是把**分散的隐式状态提炼成显式的、可直接使用的知识**。

## 2. 主流程为什么是这 10 步

| 步骤 | 为什么放在这个位置 |
| --- | --- |
| 1 确定状态维度 | 先定「记什么」，否则后面全是空转 |
| 2 设计计数器与约束 | 最高频的失效点（数不清次数导致违反上限），优先解决 |
| 3 设计 TODO 存储与工具 | 解决目标偏离，是第二高频问题 |
| 4 侧信道信息 | 时间/间隔等元数据，为时序理解打底 |
| 5 环境状态摘要 | 解决「不知道当前目录/时间」类错误 |
| 6 错误信息格式 | 解决错误后盲目重试（四层结构） |
| 7 确定注入位置 | 内容定完后统一定位置（末尾追加） |
| 8 选择更新策略 | 位置定了才有缓存代价问题 |
| 9 代码维护与投毒防护 | 实现纪律，必须在上线前定死 |
| 10 对照实验验收 | 最后验证收益 |

**顺序逻辑**：内容（1-6）→ 位置（7）→ 更新（8）→ 纪律（9）→ 验证（10）。位置与更新策略放在内容之后，是因为缓存代价取决于状态消息的大小与更新频率——内容没定就算不出来。

## 3. 为什么「瞥一眼检验」是核心验收标准

抽出状态栏单独看，模型能否**不扫描轨迹**就回答：调用几次 / 还剩几项 / 几点 / 目录在哪 / 上次为什么失败。

答不上来的维度就是要补的字段。选它的原因：直接对应失效模式（模型要「现算」就是因为状态栏没提炼到位），且不需要跑实验就能自查。

## 4. 注入位置：为什么是末尾的 user 角色消息

两个约束共同决定：

1. **注意力**：放在末尾＝空间上更接近即将生成的新 token，获得更高注意力权重（强制性的注意力引导）。
2. **KV Cache**：修改开头的 system 消息会破坏整个前缀缓存；追加到末尾则不影响任何已缓存 token。

**容易误解的点**：这里的 user 角色只是 API 协议层面的技术选择，内容并非来自真实用户——是 Harness 借用 user 这个消息槽位注入框架生成的元信息。文档里必须写清，否则使用者会以为要伪造用户输入。

## 6. 三个脚本的分工

| 脚本 | 为什么需要它 |
| --- | --- |
| `discover_context.py` | 勘察项目：是否已有计数器/TODO/状态栏、消息拼装位置、约束阈值、从轨迹估算 S/R/N |
| `status_ledger.py` | 计数器与约束检查的**参考实现**——计数必须由代码完成，这是硬纪律 |
| `cache_cost_estimator.py` | 替换 vs 追加的取舍必须算：C_replace ≈ (N−1)(1−α)R，C_append ≈ αSN(N−1)/2 |

`cache_cost_estimator.py` 存在的意义是：**更新策略不能靠直觉选**。状态小、更新间后缀长、会话短 → 追加；状态大、更新频繁、轨迹长 → 替换。

## 7. 关键取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 状态栏内容 | 写结论（3/3 已达上限），不写原材料 | 缺提炼层正是问题根源 |
| 更新策略 | 由成本模型算，不靠直觉 | 两种策略各有明确的缓存代价 |
| 谁维护状态 | 代码；即使用 LLM 也只逐条抽取 + 代码汇总 | 模型无条件相信状态栏，且批量统计易错 |
| 是否删除原始上下文 | 谨慎；状态栏是有损投影 | 一旦问到未计算的维度，准确率断崖式下降 |
