# 决策记录（ADR 式）

记录仓库层面的关键取舍、当时为什么这么定、以及什么情况下应该推翻它。

---

## ADR-1：做成「可执行的 skill」，而不是教程或 checklist

- **状态**：采纳
- **背景**：这些经验最初是读书笔记与个人习惯，散落在文档里，用的时候要靠回忆。
- **决策**：沉淀成 skill——能被 Agent 加载、按流程执行、用脚本自检。
- **理由**：教程解决「知道」，skill 解决「每次都做到」。后者需要流程、检查项与可执行的脚本，而不是一段叙述。
- **代价**：维护成本高于写文档（改一次要同步 SKILL.md、references、assets、scripts）。
- **何时推翻**：若发现使用者只想要速查表而不需要流程，则应拆出一份精简 checklist 版本。

---

## ADR-2：定位为「编码实现指导」，不是提示词模板

- **状态**：采纳（由使用者反馈促成）
- **背景**：初版 `agent-status-design` 被理解为「生成状态栏提示词模板」。
- **决策**：明确划界——产出是数据结构与管线实现，载体是代码；`assets/status_bar_template.md` 改名为 `status_render_spec.md`（输出约定）。
- **理由**：状态、计数、缓存这类东西写死在提示词里不会更新，等于没有。四个 skill 全部统一到这个定位。
- **何时推翻**：无。这是内容性质决定的，不是偏好。

---

## ADR-3：动手前「自主调研」，而不是「先问用户 8 个问题」

- **状态**：采纳（两轮反馈后定型）
- **演变**：
  1. 初版：必问清单 8 项 + 追问规则。
  2. 反馈：「问题太开放，希望从项目里得到信息，提供推荐方案供选择」。
  3. 再反馈：「不只是项目，Agent 能自己获得的信息都不用问用户——问用户也是用户去网上查」。
  4. 定型：**项目 → 文档/检索 → 线上数据/实测 → 仍不确定且属业务决策，才问用户**（≤3 个问题，带选项与推荐项）。
- **理由**：把可查证的事实推给用户，既慢又降低答案质量；完全不问又会在关键分叉点猜错。正解是先取事实、再给默认方案、只让人做取舍。
- **配套**：每个 skill 加 `discover_*_context.py` 做项目勘察（带 `文件:行` 证据，区分代码命中与文档提及）。
- **何时推翻**：若某个主题的事实无法从项目或文档获得（例如纯创意类工作），则应加强提问环节。

## ADR-4：目录与 `name` 统一用连字符

- **状态**：采纳
- **背景**：初版目录为 `system_prompt_design`（下划线），而 frontmatter `name` 是 `system-prompt-design`。
- **决策**：目录全部改为连字符，与 `name` 一致。
- **理由**：校验器要求连字符命名；目录与 `name` 不一致会在加载与引用时产生歧义。
- **代价**：早期提交历史里留有下划线路径。
- **何时推翻**：无。

## ADR-5：内容用中文

- **状态**：采纳
- **理由**：作者的工作语言与团队语境是中文；中文表达在这些主题上更精确（如「追加 vs 替换」「霸屏」）。术语首次出现时保留英文原文，便于检索与对照原著。
- **何时推翻**：若仓库面向国际受众，应做中英双版（而非替换）。

---

## ADR-6：脚本只用 Python 标准库

- **状态**：采纳
- **理由**：零依赖意味着**不需要安装步骤**就能在任何环境跑；对 skill 这种「被加载后随手执行」的场景至关重要。
- **代价**：不能用现成的向量库、分词器，算法需自己实现（如 BM25、nDCG、重要性评分）；精度是工程可用的级别，不是学术级。
- **例外**：图片处理（裁剪 logo 水印）用了 Pillow，但那是**一次性构建动作**，不在 skill 交付物里。
- **何时推翻**：若某个检查必须依赖第三方库才有意义，应单列为可选脚本并在 README 标明依赖。

## ADR-7：参考来源按许可证分级处理

- **状态**：采纳
- **背景**：内容受三本书启发，但许可证不同。
- **决策**：

| 来源 | 许可证 | 处理方式 |
| --- | --- | --- |
| 《深入理解 AI Agent》李博杰 | Apache-2.0 | 主要方法论来源，可商用可衍生 |
| 《从零开始构建智能体》Hello-Agents | CC BY-NC-SA 4.0 | 降级为延伸参考（**非商用**、相同方式共享） |
| 《Agentic Design Patterns》中译 xindoo | 未声明 | 仅列链接，不摘录不改编 |

- **理由**：CC BY-NC-SA 的非商用条款与 MIT 仓库不兼容；许可证不明的来源在取得授权前不应摘录。
- **配套**：README 声明「独立整理、未复制原文、未按原书章节结构编排」，并提供侵权下架通道（邮箱 + issue）。
- **何时推翻**：取得明确授权后可放开对应来源的摘录。

## ADR-8：用 `.gitattributes` 把语言统计改为 Markdown

- **状态**：采纳
- **背景**：GitHub 按文件字节数统计语言，6 个 Python 脚本压过 20+ 篇 Markdown，仓库显示为 Python。
- **决策**：`*.py linguist-documentation`、`*.md linguist-detectable`、`docs/images/* linguist-documentation`。
- **理由**：仓库主体是 Markdown 文档，脚本只是辅助体检工具，不应主导语言统计。
- **代价**：脚本的贡献在语言条上不可见（若想体现「文档 + 工具」双重属性，可去掉 `*.py` 那行）。
- **何时推翻**：若后续脚本规模显著增长，应重新评估。

## ADR-9：每个 skill 固定包含「调研参考」与「设计输入表」

- **状态**：采纳
- **决策**：`references/information-gathering.md` 与 `assets/requirements_intake.md` 是每个 skill 的固定件。
- **理由**：前者保证动手前不拍脑袋且留证据，后者保证结论留痕、假设可复核。两者共同解决「设计过程不可评审」这个根本问题。
- **何时推翻**：无。

---

## ADR-10：提交按逻辑单元原子拆分

- **状态**：采纳
- **做法**：一个 skill 的提交拆成 SKILL.md → references（按主题分批）→ assets → scripts → 子 README → 根 README。
- **理由**：任一提交可单独回滚而不破坏其余部分（例如只回滚脚本提交，文档仍完整可用）。
- **代价**：提交数量多。
- **何时推翻**：若需要 bisect 定位问题，更细的拆分反而是优势，故无推翻理由。
