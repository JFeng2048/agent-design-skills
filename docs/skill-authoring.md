# Skill 编写方法论：7 条设计原则

四个 skill 共享同一套方法论。本文说明每条原则是什么、**为什么这么定**，以及违反会怎样。

---

## 原则一：定位必须是「编码实现指导」，不是「提示词模板」

**做法**：SKILL.md 开篇就用表格划界——产出是数据结构与管线实现、载体是代码、关键约束由代码保证；并显式写出「不属于本 skill 的是什么」。

**为什么**：这些主题（状态栏、记忆、检索）真正的难点都在工程实现：计数谁来做、冲突谁来解决、缓存谁来保证。一旦写成模板，使用者会把它复制到提示词里，然后发现状态不会更新、计数仍然算错——**模板化的产物在这个主题上是无效的**。

**配套动作**：`assets/` 里的文件命名体现定位——是 `*_spec.md`（输出约定）与 `*_template.md`（填写表单），并注明它不是塞进 system prompt 的文本。

---

## 原则二：先自主调研，再推断默认方案，最后才问用户

**做法**：SKILL.md 里「动手前」章节固定三节——自主调研（项目 → 文档/检索 → 线上数据/实测）、推断默认方案、只有业务决策才问用户（≤3 个问题，每个给选项 + 推荐项）。

**为什么**：这两端都走过弯路。

- 先问一堆开放问题：用户也得去查同样的资料，多一轮往返且答案质量更差。
- 直接给「通用方案」：关键分叉点（计数维度、更新策略、存储格式）全猜错，返工。

正确顺序是**先从项目里取事实**（代码、配置、日志都能读到），**推断出可落地的默认方案**（用户不选也能开工），**只把真正需要人拍板的业务决策拿出来问**，且必须给选项与推荐项。

**配套动作**：每个 skill 都有一个 `discover_*_context.py` 脚本做项目勘察，输出带 `文件:行` 的证据，并区分「代码命中」与「仅在文档中提及」——避免把文档里的讨论误判成已实现。

---

## 原则三：渐进式披露，主文件保持精简

**做法**：加载路径固定为三段——

```
frontmatter 元信息（决定是否被触发）
  → SKILL.md 主流程（决定怎么做，一次性读入）
  → references/*.md（按需加载，用到哪篇读哪篇）
```

SKILL.md 只放流程、自检清单、反模式与索引；深度内容（公式、对比表、实验结论）全部下沉到 references，并在 SKILL.md 末尾写明「按需读取，不要一次性载入」。

**为什么**：skill 的元信息常驻上下文。**主文件越短，被触发时的成本越低**；而深度内容只在真正需要时才付出代价。这也正好复用了本仓库自己在讲的原理——静态前缀要小，动态内容按需追加。

---

## 原则四：references 按「决策点」拆分，不按章节拆分

**做法**：每篇 reference 对应一个**具体的设计决策**，标题就是决策名。例如 `rag-design` 里分块、稠密、稀疏、混合、配额各一篇，而不是「第三章第一节」。

**为什么**：使用者不会按顺序读书，他是带着问题来的（「两路结果怎么合并」）。按决策点拆分才能被精准检索到。同时，单篇过长会失去渐进式披露的意义。

**判据**：一篇 reference 读完后，使用者应该能**做完一个决定**；做不到就说明还要再拆或内容不足。

---

## 原则五：能用代码算的，绝不让 LLM 心算

**做法**：每个 skill 都配脚本，承担计数、阈值比对、PII 检测、成本估算、指标计算、配额分配等确定性工作；并在文档里写明「这些必须由代码完成」。

**为什么**：这不是风格偏好，是这些主题的核心失败模式——LLM 做数量统计本来就容易错，而且模型会无条件相信已经写好的结论（状态栏投毒风险正来源于此）。把统计交给代码，既准确又可审计。

**配套动作**：脚本只用 Python 标准库，零依赖、可单测、延迟可忽略。

---

## 原则六：交付前自检清单 + 反模式表，作为质量的落脚点

**做法**：每个 SKILL.md 都有「交付前自检清单」（分组的复选框）与「常见反模式表」（反模式 / 后果 / 修正三列）。

**为什么**：这类工作的价值不在知道多少知识点，而在**每次都能稳定地不漏掉关键项**。清单把「检查」这件事从记忆变成流程；反模式表则把踩过的坑固化下来——它比正面描述更能防止复发，因为人更容易认出错误形态。

**写法要求**：反模式必须写「后果」，否则使用者不知道为什么不能那样做。

---

## 原则七：内容用中文，命名用连字符，frontmatter 的 description 要写清触发条件

**做法**：

| 项 | 约定 | 为什么 |
| --- | --- | --- |
| 内容语言 | 中文 | 作者的工作语言与团队语境是中文；术语首次出现时保留英文原文便于检索 |
| 目录名 | 连字符（如 `user-memory-design`） | 与 frontmatter 的 `name` 一致，避免加载歧义 |
| frontmatter `name` | 与目录名相同 | 校验器要求连字符命名 |
| frontmatter `description` | 写清**适用场景 + 使用时的行为要求** | description 决定 skill 是否被触发；只写主题会漏触发，写上「使用本 skill 时须先自主调研」能直接约束执行行为 |

**为什么强调 description**：它是唯一常驻上下文的元信息。把「先调研再动手」写进 description，比写在 SKILL.md 正文里更有效——后者只有在被触发后才读得到。

---

## 附：一个 skill 的标准骨架

```
<name>/
├── SKILL.md                定位声明 + 动手前（自主调研）+ 设计流程 + 交付物
│                           + 自检清单 + 反模式 + 参考资料索引
├── README.md               安装（npx skills add）+ 症状→入口对照表
│                           + 目录结构 + 脚本用法 + 关键纪律
├── references/
│   ├── information-gathering.md   固定存在：自主调研清单
│   └── <按决策点拆分的若干篇>
├── assets/
│   ├── requirements_intake.md     固定存在：设计输入表
│   └── <交付模板若干>
└── scripts/
    ├── discover_*_context.py      固定存在：项目勘察
    └── <体检/计算/评估脚本若干>
```

两个「固定存在」的文件是有意的：**调研**保证动手前不拍脑袋，**设计输入表**保证结论留痕可复核。
